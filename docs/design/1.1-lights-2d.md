## 1. Problem

The yardstick game of release 1.1 is a top-down station where each player
sees only what is near and not behind a wall, and where the lights can be
sabotaged. That needs four things the engine did not have:

- **line of sight**: "can A see B" and "what is visible from here", against
  the station's walls (the tilemap's solid tiles) and against doors (entities
  with colliders), answered the same way in game code, in replication and in
  the tools;
- **hidden information that follows walls**: `NetVisibility::Sight` must stop
  sending a player what is behind a wall (until now it was `Near`);
- **2D lights**: point lights in the plane with a colour, a radius and an
  intensity, an ambient level, and shadows cast by the same walls, lighting
  sprites and tilemaps;
- **a player's vision** drawn as darkness with a soft edge around what the
  character sees: the genre's "a circle around you, cut by walls".

And the engine's rules hold: the visibility polygon feeds the simulation and
replication, so it must be **bit-stable**; every new look setting is **off by
default** and every old picture stays byte-identical; everything is
observable from the control plane with a headless test.

## 2. Where line of sight lives

Options:

1. In `wish_physics`, beside the tile shapes, with Rapier's ray casts.
2. In a new small crate below the simulation, `wish_sight`, with geometry of
   its own and no outside library.

Rapier's queries are 3D, built from shapes held in its own state, and the
physics state exists only in a session; line of sight is also needed by
replication (`wish_replicate`, which must not pull Rapier in), by the
renderer (shadows of 2D lights, in a scene that is not running), and by
`describe_view`. A 2D visibility polygon is a few hundred lines of plain
geometry, and the determinism argument is simpler when every operation is
ours. Decision: **2, `wish_sight`** (depends on `wish_core`, `wish_ecs`,
`wish_app` for its system, `wish_types`; no outside crate).

The tile shapes (`MapShapes`, `TileShapes`, `install_tile_shapes`) move
from `wish_physics` down into `wish_sight`, because both physics and sight
read them; `wish_physics` re-exports them, so every caller is unchanged.

## 3. Occluders

**What blocks sight and light:**

- **Tile walls:** the solid tiles of colliding layers of every `Tilemap`
  whose map has shapes (the same boxes and outlines physics builds walls
  from, 1.1-tilemaps §7). A wall that collides blocks sight; a decoration
  layer (`collide: false`) does not.
- **Entities with an `Occluder` and a `Collider`:** the collider's outline in
  the X–Y plane (the 2D profile's reading: `Box` a rectangle of
  `size.x` × `size.y`, `Sphere` a circle of the larger of the two, `Capsule`
  a rounded rectangle along Y, `Cylinder` a rectangle), placed by the
  entity's world transform. Doors are entities: a closed door has
  `Occluder { enabled: true }`, an open one sets it false (or moves away).
  An `Occluder` without a `Collider` blocks nothing (`check` warns
  `occluder_without_collider`).

**The occluder set** (`wish_sight::Occluders`) is a list of segments in the
world's X–Y plane, each with the entity it belongs to, plus a uniform grid
(4 m cells, `BTreeMap` by cell, so iteration is ordered) for lookup. Boxes
contribute their four edges; outlines and round shapes their edges (circles
and capsule ends from a fixed table of directions, §4). Segments are made in
a fixed order: tilemap entities in entity order, their boxes then outlines in
the order of `MapShapes`; then occluder entities in entity order. Interior
edges between neighbouring boxes are kept: they change nothing (a ray that
crosses one is already inside a wall) and finding them costs more than they
do. Limits: 65,536 segments (beyond them the rest is left out, with the
warning `sight_occluders_cut_short` in the answer of `physics_query sight`), and a
grid cell count per segment of 4,096 (a longer segment goes to a short list
every query checks).

**When it is built.** A system of its own, `sight` (a reserved name, like
`physics`), runs after transform propagation and rebuilds the set every tick
when the world has anything that occludes; otherwise it removes it. The set
is a world extension (ADR-026: carried by snapshots, not part of the world
hash; everything in it is derived from components every tick, so a restored
snapshot continues bit for bit). `wish_sight::prepare` builds it when a
session starts, so questions during tick 0 see the walls. Game code asks
during a tick and sees the set **as of the end of the previous tick** (as
`raycast` sees the physics world as of the start of the tick: the answer does
not depend on system order); replication sends after the systems and sees
the set the `sight` system just built. A world that never ran `sight` (a
scene view, a picture) is asked through `wish_sight::current`, which builds
the set on the spot.

## 4. The visibility polygon, deterministically

**Can A see B** (`Occluders::can_see(a, b, ignore)`): true when the segment
from A to B crosses no occluder segment, where touching counts as crossing
(a ray along the shared edge of two wall boxes, or exactly through a wall
corner, is blocked: there is no gap there). The segments of up to two
entities can be ignored, so an entity's own outline (a door asked about
itself, a character with an occluder) does not hide it. The test is four
orientation signs in `f64`, with the collinear case handled by overlap of
the boxes.

**What is visible from here** (`Occluders::visible_polygon(origin, radius)`):
the classic angular sweep by rays:

1. The segments whose box meets the circle's box, from the grid, sorted and
   without repeats (at most 1,000; beyond that the first by index).
2. Directions: towards every segment end inside the circle and two that pass
   just beside it on either side (turned by ±0.0001 rad with fixed
   constants); towards every point where a segment crosses the circle; and
   128 fixed directions around the circle, so the edge of the circle is
   drawn where nothing blocks.
3. Along each direction, the nearest segment hit within the radius; the
   point there, or on the circle. The walls are put into a 32 × 32 grid of
   the circle's box (each in every cell its box, widened by a millionth of
   a cell, meets); a ray walks the cells outward from the origin and stops
   once its nearest hit is nearer than the next cell's edge, which gives
   the same nearest hit as testing every wall (§10).
4. The points sorted by angle; ties by the order of their direction.

**Bit-stability.** Every number is `f64` made from the world's `f32`; the
only operations are `+`, `-`, `*`, `/`, `sqrt` and comparisons, which IEEE
754 defines to the bit, and Rust never fuses them into a multiply-add. No
trigonometry at run time: the 128 directions are a table computed by a
`const fn` (a Taylor series of plain arithmetic, evaluated by the compiler),
and angles are compared by a pseudo-angle (`dy / (|dx| + |dy|)` arranged
into four quadrants: monotone in the angle, division only). Sorting uses
`total_cmp` and then the direction's index: a total order. The output points
are rounded to `f32`. Iteration is over `Vec`s and `BTreeMap`s only. A test
records the polygon of a room with a door as golden numbers (the count and a
`StableHasher` digest of the bits) and runs it twice; the suite runs in debug
and release, and CI on Windows and Linux.

**Cost** is bounded by the limits: at most 1,000 segments and 8 × 1,000 +
128 directions per polygon (three per segment end, two per crossing of the
circle, the circle's own), each tested against the segments in range (the
grid keeps that to the walls near the origin in a station).
Measured: §10.

## 5. Game code

No new import: the answer goes through the import that already answers ray
casts, `wish.physics_query(request, len, out, capacity)`, with two new
request kinds (the first byte; `1` is the ray): `2` **can see** (from, to,
an entity to ignore) and `3` **visible area** (from, radius, at most 8,192
points back: a polygon has at most 8,128). The ABI version is unchanged: a module built against an older
SDK never sends these kinds, and an older engine answers an unknown kind
with `-1`, which the SDK reads as "cannot answer" (`false`, an empty area).
Fuel: the fixed cost every query pays (`QUERY_FUEL`, 20,000), plus
`WORK_FUEL` (4) per wall segment the question tested, charged after the
answer (deterministic: the same world gives the same count). The largest
visible area (1,000 walls, 8,128 rays) costs about 32 million of a call's
100 million.

SDK (`wish_sdk::sight`, in the prelude): `can_see(from, to) -> bool`,
`can_see_ignoring(from, to, entity)`, `visible_area(from, radius) ->
Vec<Vec2>` (world X–Y, in angular order around `from`; empty when the engine
cannot answer). They see the walls as of the end of the previous tick.

## 6. Replication: `Sight`

`Sight` now means `Near` **and** a line of sight from one of the player's
`NetViewer` points to the entity, ignoring the outlines of the viewer and of
the entity. Positions are the X–Y of the same positions `Near` uses. The
occluders are the world's `Occluders` extension; a world without one (no
walls, or a host that never ran `sight`) gives exactly `Near`, so the rule
can only ever remove players, never add them (1.1-replication §3.1). The
owner still always sees its entity. Cost: one segment test per (player,
viewer, candidate) within the radius.

## 7. The control plane

`physics_query` gets a fourth question, **`sight`**: `{from: [x, y], to:
[x, y]}` answers `visible` (and the first occluder in the way, `blocked_by`,
when one is); `{from: [x, y], radius: r}` answers the visible area as
`points` (rounded to millimetres for the answer). In a scene or a session,
like the other questions, with the walls of the project's tilemaps as they
are on disk. `describe_view` lists `lights_2d` (entity, position, radius,
how many points its lit area has) and `vision` when a picture has them, and
the picture's `stats.effects` names `lights_2d` and `vision` when they were
drawn.

## 8. 2D lights and vision

### 8.1 Types (`wish_types::lights2d`, registered with the render types)

| Type | Kind | Fields (defaults) |
|---|---|---|
| `Lighting2D` | resource | `enabled` (false), `ambient` (linear colour, 0.2 grey) |
| `Light2D` | component | `color` (white), `intensity` (1, 0 to 100), `radius` (5 m, 0 to 1000), `shadows` (true) |
| `Vision2D` | component | `enabled` (true), `radius` (6 m), `softness` (1.5 m), `darkness` (linear colour with alpha, `[0.02, 0.02, 0.04, 0.9]`) |
| `Occluder` | component | `enabled` (true) |

**2D lighting is off by default** (`Lighting2D.enabled: false`), and a
scene without a `Vision2D` draws no darkness, so every existing picture is
byte-identical (checked by the golden tests of sprites, sheets and
tilemaps, which did not change). With `enabled` the sprites and tilemaps
are lit: each picture's colour is multiplied by the ambient plus every
light's contribution. A `Light2D` while 2D lighting is off warns
`light_2d_without_lighting` (in `check` and in the picture's warnings). A
light's contribution falls off smoothly to zero at its radius
(`(1 − d/r)²`), times its colour and intensity; with `shadows` it reaches
only its visible polygon (§4). Particles and the interface are not lit
(they are drawn as before; particles glowing in 2D is release 1.9's HDR
work). Sabotaging the lights is game code writing `Lighting2D.ambient` or
the lights' `intensity`.

**Vision:** every enabled `Vision2D` (on a player's character, say) shows
what is within `radius` of it and not behind a wall; the rest of the
picture is covered by `darkness` (its alpha is the strength). The edge of
the circle is soft over `softness` metres; a wall's cut is sharp. Several
visions show the union of what they see; the first in entity order gives the
darkness colour. A client of an online game enables only its own player's
vision (game code knows who it is).

### 8.2 Drawing: a light texture, measured

Options for lighting sprites with shadowed lights:

1. **A light texture:** before the sprites, every light's visible polygon is
   drawn as a fan of triangles into a texture the size of the picture,
   cleared to the ambient colour and added to with each light's falloff; the
   sprites multiply their colour by the texel under them.
2. **Per-light polygons over the finished picture:** sprites drawn with the
   ambient, then each light's polygon blended over the picture
   (`dst × (1 + light / ambient)`). No texture, but it lights everything under
   the polygon (the 3D picture, the background, particles), bands in an
   8-bit target where the ambient is dark (a value of 0.05 multiplied back
   by 10), and breaks when the ambient is 0.
3. **Per pixel in the sprite shader:** every sprite fragment loops over the
   lights. Shadows would need each light's polygon per fragment: a
   point-in-polygon test per light per fragment, or a shadow map per light.

Decision: **1, a light texture** at the picture's size (`Rgba16Float`, so
lights add up beyond 1 before they multiply). It is the only option that
lights exactly the sprites, with shadows, at a cost that grows with the
lights' area on screen and not with the sprites' overdraw. Its cost was
measured over the yardstick's kind of map (§10); option 2 was rejected for
what it draws wrongly, not for its speed, and option 3 because a shadow per
fragment per light is the expensive part the light texture avoids.

The sprite pass gets a second fragment entry point, `fs_lit` (the old
`fs_main` is untouched: the M12 look rule), used through its own pipeline
only when 2D lighting is on; particles in it are not lit. The light texture
is drawn by a new shader, `light2d_pass.wgsl` (`vs_fan`, `fs_light`,
`fs_vision`, `vs_screen`, `fs_darkness`, all in `ENTRY_POINTS`). Vision is a
mask texture (`R8Unorm`, the fans with `max` blending and the soft edge)
and one full-picture triangle after the sprites and particles, before the
interface, blending `darkness` by `1 − mask`. All of it follows the GPU
rules: targets and buffers from the pool, bind groups built in the frame,
everything inside `Gpu::checked`, no division by zero in the shaders (a
radius is at least 1 mm on the CPU before it is sent). Fans are built on the
CPU from the polygons of §4, which extraction computes (the renderer never
reads the world).

**Pool budget.** A 4K picture with 2D lights and vision adds the light
texture (8 bytes a pixel, 63 MiB) and the mask (1 byte a pixel, 8 MiB):
71 MiB. A 2D scene uses neither bloom nor cascades, so its own peak is far
below the budget; with every 3D effect on as well the arithmetic is 473 MiB,
so the budget goes from 448 MiB to 480 MiB.

## 9. What it changes

- New engine types `Light2D`, `Lighting2D`, `Vision2D` (render types) and
  `Occluder` (sight): the registry fingerprint and so the world hash of every
  world that registers the engine's types moves, as with every package that
  adds a type (M12-render-foundation §6). No recorded hash in the repository
  covers these registrations: `wish_physics`' recorded station and pile
  hashes register physics types only and did not move.
- `crates/wish_scene/src/defaults/format-2.json` gains the four types
  (`UPDATE_DEFAULTS=1 cargo test -p wish_control --test look_lock`);
  `format-1.json` is unchanged.
- `Sight` replication narrows to line of sight where walls exist.
- Game code compiled against an older SDK keeps working; it needs a rebuild
  only to use the new functions.
- **A bug found on the way:** the request decoder of game code's ray casts
  (`wish_sdk::physics::Ray::decode`) returned "not a request" whenever the
  ray named no entity to ignore, so `raycast(from, dir, max)` was never
  answered (only `cast` with `ignore: Some(..)` was, which is all the
  physics test used). Fixed, with a unit test for both forms and a
  `raycast` without `ignore` in this package's scenario test. Game code
  built against an older SDK keeps sending the same bytes, so it is fixed
  by the engine alone.

## 10. Measurement

`cargo test --release -p wish_render --test lights2d measure -- --ignored
--nocapture` (`WISH_BENCH_HARDWARE=1` for the hardware adapter): a 64 × 64
tilemap of 8 × 8 rooms with doors (two layers, 8,192 tile rectangles), at
1280 × 720 under an orthographic camera that shows the whole map; 16 lights
of 10 m radius spread over it; a vision of 12 m. Medians of 10 frames after
3 to warm up; "areas" is extraction on the CPU (every light's and vision's
polygon), timed once. Two sets of walls: **one box per solid cell** (783
boxes, 3,132 segments: far more than the engine's box merging gives, the
hard case) and **rows merged** (432 boxes, 1,728 segments). Windows 10
19045, Ryzen 5 5600 pinned to four cores at below-normal priority, release,
22 November 2026, with another lane building on the other cores (the
software adapter's frames moved by about ±10 % between runs).

| Adapter | Walls | Tilemap alone | 16 lights, shadows | 16 lights, no shadows | Vision alone | Lights and vision | Areas on the CPU (lights, shadows) |
|---|---|---|---|---|---|---|---|
| Software (WARP) | one box per cell | 156.5 ms | 283.5 ms | 216.0 ms | 173.6 ms | 264.9 ms | 5.6 ms |
| | rows merged | 175.8 ms | 267.3 ms | 193.0 ms | 173.5 ms | 257.2 ms | 3.3 ms |
| Hardware (RTX 3060 Ti) | one box per cell | 3.4 ms | 4.6 ms | 4.0 ms | 4.0 ms | 4.7 ms | 5.0 ms |
| | rows merged | 3.2 ms | 4.0 ms | 3.7 ms | 3.3 ms | 4.1 ms | 2.4 ms |

What it says:

- **On hardware the light texture is cheap:** 16 shadowed lights add about
  1 ms to the frame, and a vision about 0.5 ms. The cost is on the CPU
  (the polygons): 2.4 ms for 16 lights over merged walls, 5 ms over a wall
  per cell.
- **The CPU side was measured twice.** The first version tested every
  wall in reach for every ray: 33 ms (per cell) and 10 ms (merged) for the
  16 lights, too much for a 60 Hz frame. Each ray now walks a small grid
  of its own outward and stops at the first wall (§4, `Local` in
  `occluders.rs`); the polygon's bits did not change (the golden digest is
  the same; the room's polygon now takes 343 wall tests instead of 4,640).
- **On the software adapter** the lit sprites (a `textureLoad` per
  fragment of 8,192 tiles) and the light texture cost about 40 to 60 ms,
  and shadowed lights about 70 ms more than unshadowed ones: WARP pays per
  triangle, and a shadowed light is about 400 thin triangles against 128.
  This is the CI and headless case, where pictures are few; a measured
  trigger for work: a yardstick game that needs more than 16 shadowed
  lights on screen at 60 Hz on hardware.
- **Option 2 and 3 were not built to be timed.** Option 2 draws the wrong
  thing (§8.2). For option 3, the light texture's own cost on hardware
  (about 1 ms with shadows) is the ceiling any per-fragment scheme would
  have to beat while also doing a shadow test per light per fragment.

## 12. Not in this package

- A tile property for walls that collide but do not block sight (windows),
  and occluders without a collider: when the yardstick game needs them.
- Soft shadows (penumbrae) and normal-mapped 2D lights.
- Lighting particles and the interface; spot and directional 2D lights.
- The editor's 2D mode shows lights as they are drawn; gizmos for a light's
  radius and an occluder's outline come with package 8.
