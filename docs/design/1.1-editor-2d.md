## 1. Problem

The yardstick game of release 1.1 is pixel art seen from above. Three things
were missing in the engine and one in the editor:

- **Pixel art shimmered.** An orthographic camera showed `ortho_height`
  meters over whatever window it had, so a game pixel was 2.37 screen pixels
  in one window and 3.1 in another, and a sprite moving by a fraction of a
  pixel changed which screen pixels its texels covered.
- **Drawing order was ad hoc.** `Sprite.layer` was a number, and the only way
  to sort characters by height was `Tilemap.y_sort` on a map of that layer.
- **Game code could not ask where the pointer is in the world.** `Pointer`
  said interface pixels only; a top-down game that walks to a click had to
  redo the camera's arithmetic.
- **The editor's view was a 3D fly camera** in every project: no top-down
  view, sprites could not be clicked (they are not in the identity buffer),
  there was no rectangle selection and the handles moved things in Z.

## 2. The pixel-perfect camera

Options: (a) fields on `Camera`; (b) a component beside it. Decision: **(b),
`PixelCamera`** (`wish_types::render`): `resolution` ([u32; 2], 320 × 180),
`pixels_per_unit` (16), `letterbox` (true), `bars` (black), `snap` (true).
A 3D camera never carries what it does not use, the inspector's `Camera`
stays short, and adding it is how a person or an agent says "this is a pixel
game" (the plan: "by addition, off by default").

**The fit** (`PixelCamera::fit`, one function for drawing, the pointer and
the editor): the scale is the largest whole number `s` with `s × resolution`
inside the window (at least 1); the game's picture is `s × resolution`
pixels, centred (an odd remainder leaves its extra pixel on the right and at
the bottom); the camera's position is drawn at the game picture's middle
pixel corner. The projection is orthographic with bounds worked out from
that corner, so it covers the **whole window**: with `letterbox` the rest is
painted with `bars`, without it more of the world shows, at the same whole
scale.

Options for the bars: (a) render the game at its own resolution into a
target and scale it up; (b) render at the window's size with the projection
above and paint the bars after. (a) would draw the interface at 320 × 180
(unreadable text) and every effect at low resolution; (b) keeps the
interface sharp and changes nothing in the passes. Decision: **(b)**: the
bars are painted on the read-back picture (`renderer::paint_bars`), the
identity buffer is cleared there (`describe_view` and clicks see nothing in
the bars), and the in-game interface fits inside the game's picture, never
the bars (`ui::fit`).

**Snapping** (`snap`): the camera's view matrix is rounded so that the
world's origin lands on a corner between game pixels
(`PixelCamera::snap_view`, in its own plane); each sprite is shifted so that
its first corner lands on one too, and each tilemap so that its origin does
(`CameraView::snap_offset`). A sprite whose pixels per meter equal the
camera's then draws every texel as an `s × s` square, and moving it by less
than half a game pixel draws the very same pixels. 3D surfaces are not moved.

**Rules kept:** a camera without `PixelCamera` draws exactly as before (every
existing golden image is byte-identical); the editor's own eye drops the fit
(`FlyCamera::apply` sets `pixel: None`: the bars are the game's, not the
editor's); all GPU work is unchanged (the bars and the snap are CPU work).

## 3. Sorting layers

The plan asked for "named layers in a project or scene resource, an order
within a layer, y-sorting". Options for the names: (a) a resource with a
fixed array of named layers; (b) the project file; (c) a component on an
entity of its own per layer. A resource is plain data of fixed size, so (a)
would make every scene that names one layer write all sixteen entries (files
must give fixed arrays whole: `wrong_length`); (b) is outside the world, so
sessions, snapshots and the renderer would need a second way in. Decision:
**(c), `SortingLayer { name, layer, y_sort }`** (`wish_types::sprite`): any
number of layers, each a few lines in the scene file, edited in the
inspector like any component, carried by every world path (scenes,
sessions, snapshots, previews), found by extraction
(`RenderScene::sorting_layers`).

- **Order:** `layer` (lower first), then **`order`** (new on `Sprite` and on
  `Tilemap`, default 0: by addition), then height on a y-sorted layer, then
  distance, stable in entity order (`sprites::draw_order`, one comparator for
  drawing and for picking). Unity's order in layer comes before its sort
  axis the same way.
- **Y-sorting** of a layer is asked by a `SortingLayer` with `y_sort` or, as
  before, by a `Tilemap` on it with `y_sort` (kept: a map's own flag is what
  1.1's tilemap package wrote).
- **Names:** `describe_view` gives a sprite on a named layer its
  `sorting_layer`, and one with an order its `order`; other answers are as
  they were.

## 4. The pointer in the world

`Pointer` gains `world` ([f32; 2], meters) and `in_world` (bool): the point
of the world's XY plane (z = 0) under the pointer, through the **main camera**
(the first entity with a `Camera`, as drawing takes it) as it stood at the
start of the tick. It is computed by the engine in `wish_input::apply`
(deterministic: from the world and the input only), so game code, scenario
tests, replays and the SDK see it with no new import.

**The picture's size.** Where the plane point is depends on how much of the
world the window shows. A window's step (`Workspace::play_step`, used by
`wen play`, the editor and exported games) puts the picture's size into the
input as `pointer.screen` (a name no action can have), so it is recorded in
replays like every input; a tool's `pointer` (interface pixels) is taken
over the interface's virtual screen. The interface position itself is now
mapped through the game's picture (`wish_input::picture_to_interface`), so
under a letterboxing pixel camera a click in the bars is outside the
interface, and the interface and the world agree on where the pointer is.

**`describe_view` with `point`** answers `under_point`: `world` (the pixel's
place in the XY plane through the chosen camera) and `sprites` (the sprites
under it, the one drawn in front first, by their drawn rectangle where their
picture's alpha times the tint's is at least 0.1: `Renderer::sprites_under`).
In the bars: none.

## 5. The editor's 2D mode

`wish_editor::view2d` (pure arithmetic, unit-tested) and the view code in
`app.rs`:

- **When:** a 2D project's scene view starts in it (the kind is read from
  `project_info`, the one place); the view's floating **2D** button, *View >
  Switch the scene view between 2D and 3D* and the command `view.mode_2d`
  (no default shortcut) switch; once switched by hand the project's kind no
  longer decides. The 3D mode is unchanged.
- **The eye** (`FlatEye`): orthographic, looking down -Z from 1000 m above
  the plane, its middle and its height in meters; made from the scene's first
  camera (a pixel camera's game picture, or `ortho_height`, or 10 m).
- **Moving:** the wheel zooms toward the pointer (the world point under it
  stays under it); the middle button, Space or Alt with the left button grab
  the world (it follows the pointer exactly); there is no orbit, no looking
  around and no flying (right button, mouse deltas and WASD do nothing).
  Framing (F) fits the selection's boxes on the view (or its place).
- **The grid:** drawn over the view in theme colours, its cell the scene
  camera's game pixel when it is a `PixelCamera`, else the first tilemap's
  cell, else half a meter, thinned to every 2nd, 4th... line when lines would
  be closer than 8 pixels; the world's axes through the origin.
- **Picking:** sprites and tilemaps are not in the identity buffer, so a
  click asks the control plane (`Workspace::render_flat`: the same camera as
  the picture): a sprite drawn in front at that pixel (by its rectangle and
  alpha: a click on a clear corner falls through), else what the identity
  buffer has there, else a tilemap with a tile there. This is used in the 3D
  mode too (sprites could not be clicked there before), and the boxes around
  selected sprites and tilemaps come from the same answer.
- **Rectangle selection:** a left drag that starts on no handle draws a
  rectangle; on release everything whose box on the view meets it is
  selected (Ctrl adds), and the status bar says how many.
- **Handles:** move along X and Y only, and with the centre square in the
  plane; rotate about Z only; scale X and Y. With *Snap* on, a move puts the
  place on the grid (pixels or tiles) instead of moving by half meters.
  Every drag is one `edit_apply` by `human`, as before.
- **Create** (and dropping an asset) puts new things in the middle of what
  the view shows, in the plane (a camera keeps its distance in front of it).
- **R6:** the split and maximizing are the window's and work unchanged; the
  eye fits whatever area the view has.

New interface text (two strings, in all 11 languages): the switch's name and
the 2D mode's hint line. No new tool and no new `edit_apply` operation, so no
parity row: every change the mode makes is an existing call.

## 6. What it changes in the world's types

- New engine components `PixelCamera` and `SortingLayer` (registered last in
  `wish_render::components::register`, in the SDK and its prelude); new
  fields `Sprite.order`, `Tilemap.order`, `Pointer.world`,
  `Pointer.in_world`. World hashes of worlds with these types move, as with
  every package that added a type (M12-render-foundation §6); no recorded
  hash in the repository covers them.
- `crates/wish_scene/src/defaults/format-2.json` gained them
  (`UPDATE_DEFAULTS=1 cargo test -p wish_control --test look_lock`);
  `format-1.json` is unchanged.
- Game code compiled against an older SDK must be rebuilt (`wen sdk`, then
  `script_build`): `Sprite`, `Tilemap` and `Pointer` changed layout.

## 8. Not in this package

- A tile palette docked to the 2D view, and painting with the 2D mode's
  own shortcuts: the palette stays under the inspector's `Tilemap` (package
  5); it works in the 2D view as it did.
- Picking an occluder's or a light's outline in 2D, and handles for a
  sprite's `size` (nine-slice) on the view: later in 1.1 if the yardstick
  game needs them.
- `PixelCamera` and 2D lights: the light texture is drawn at the window's
  size, so lights are smooth over pixel art (a game-pixel light texture is a
  later choice).
- The camera used for `Pointer.world` is the main one; a game with split
  screens or several cameras reads its own (release 1.7, with viewports).
