**Status (22 November 2026):** in progress on branch `r1.1`, in parallel
lanes next to the 1.0 beta (the user's decision of 21 November: go faster with
several agents). Done: packages 1 to 15, each with its own design note

## 1. Request and decisions

The user, 21 November 2026, after comparing engines: 2D and multiplayer
score far too low, and the engine must go far in both early, because the
user wants to have a hidden-role party game made with it (the genre of
Among Us), and wants the engine to be strong at that kind of game. Opening a
project should separate 2D and 3D projects, with their own templates and
defaults, as other engines do.

Decisions of the same day (the user's):

- **1.0 ships as it is** (the short path, the beta 0.9.0 already out). Release
  **1.1 is given wholly to 2D, online play and project kinds.** The 2D kit
  moves up from release 1.7, and online play from after 2.0. This grows the
  train's 1.1: it is a double release (about 30 packages).
- **Connection:** first the local network, a direct address and a room code,
  plus a relay program that ships with the engine (`wen relay`) and that the
  user can run on any small server when they want internet play. No hosted
  service, no account and no fee now. Steam networking may be added later
  next to these, never instead of them.

Technical decisions (made here, recorded in ADR-029): the network model is
**host-authoritative replication with client prediction**, not lockstep and
not peer-to-peer rollback (section 3).

## 2. The yardstick: a hidden-role party game

Release 1.1 is done when an original hidden-role party game, made only with
the engine's tools (the M7 method: every place we get stuck is written into
`docs/friction.md` and fixed in the engine), is played by 4 to 10 people on a
local network and through a relay, and its scenario tests play it with bots
over a simulated, lossy network in CI. Working name: `examples/station`; built
as **Ridgewatch**, `examples/ridgewatch` ([1.1-ridgewatch.md](1.1-ridgewatch.md)).
It is an original game in the genre, with its own name, map, characters and
art; it copies no existing game.

What such a game needs, and where it comes from:

| Need | Package |
|---|---|
| A top-down map with walls, rooms, doors and vents | tilemaps, 2D physics profile, editor 2D mode |
| Characters that walk, with walk cycles and colours | sprite sheets and animation, tint |
| Seeing only what is near and not behind a wall | 2D vision (line of sight), 2D lights |
| Hidden roles: a player must not receive what they may not see | replication with per-player visibility |
| Smooth own movement despite latency | client prediction and reconciliation |
| A lobby with a room code, ready, start, leave, rejoin | lobby and sessions |
| Meetings, chat, votes, task mini-games | targeted messages, in-game interface |
| Ghosts seen only by ghosts | visibility rules |
| Playing over the internet | `wen relay` |
| Proving it works without six people | network simulator, bots, scenario tests, replays |

## 3. The network model (ADR-029)

**Host-authoritative.** One machine, the host (a player's own game, or a
headless host), runs the one true simulation: the same deterministic
simulation as a single-player game, with the inputs of every player. The
other machines send their inputs, stamped with the tick they meant, and
receive the state they may see.

**Why not lockstep.** In lockstep every machine runs the whole simulation from
everyone's inputs, so every machine knows everything: in a hidden-role game
any player could read who the saboteur is. One slow machine also stalls
everyone, and joining a running match is hard. **Why not rollback first.**
Peer-to-peer rollback has the same "everyone knows everything" property; it is
right for fighting and action games with no hidden information and comes
later (release 1.7), built from the same parts (snapshot, restore, inputs per
tick).

**What determinism gives the network.**
- The host's input log is a replay: any match can be played again, bit for
  bit, and a bug report is a file.
- The network itself can be simulated deterministically (latency, jitter,
  loss and reordering from a seed). A scenario test plays ten bots over a bad
  network in one process, in CI, with the same result every time. An agent
  can test a multiplayer game without people: this is the engine's argument
  (proof, not generation) applied to netcode.
- Prediction is exact: a client restores the last state the host confirmed
  (`World` snapshot) and replays its own unconfirmed inputs through the same
  systems; when nothing was lost, the prediction equals the host's result.

**Replication.** A component is sent only if its entity is `Replicated`.
Every replicated entity has a visibility rule: everyone, its owner only,
players within vision (line of sight over the tilemap), a group (for
example ghosts), or a filter written in game code. The host sends each player
a delta of what that player may see against the last snapshot the player
acknowledged, encoded by the schema (the engine already knows every field's
type and range). What a player may not see never leaves the host.

**Game code** never opens a socket (the sandbox of ADR-011 stands; the engine does all networking). It sees players
(`Players`, `PlayerId`), the inputs of each player (`Actions::of(player)`),
whether it runs on the host, and targeted messages (to the host, to a player,
to everyone). The same game code runs single-player, as a host and as a
client.

**Transport.** A small protocol of our own over UDP (`std::net::UdpSocket`)
in a new wrapper crate, `wish_net`: a handshake with a room code, a reliable
ordered channel for messages and an unreliable one for state, fragmentation,
acknowledgements, rate and size limits. Local discovery by broadcast.
Traffic is authenticated and encrypted with a reviewed library under a
permissive licence (the crate is chosen in the transport package; its licence
is checked as for every dependency). **A hostile peer cannot crash or freeze
the host:** packets are fuzzed like hostile game modules (invariant 7).

**The relay** (`wen relay`) forwards packets between a host and its players
by room code. It runs no game logic, stores nothing and limits rates. It is a
plain program in both archives; the guide shows how to run it on a small
Linux server.

**Limits of 1.1, said in the public text:** no host migration (if the host
leaves, the match ends), no dedicated server fleet, no matchmaking service,
no voice, no rollback. Online play is a **preview** in 1.1 (ADR-028 rule 1)
until its committed network replays give the same hashes on Windows and
Linux in CI; then it is supported.

## 4. The 2D kit

Moved up from release 1.7 and enlarged by what the yardstick game needs.

- **Sprite sheets and sprite animation** (a `*.sheet.json` file: frames,
  clips, timing; a `SpriteAnimator` component), nine-slice, tint; sprites
  kept on the GPU and drawn in batches.
- **A 2D physics profile.** First decision of the package: the pinned 3D
  Rapier constrained to a plane (no new dependency, determinism already
  proven on Windows and Linux) against `rapier2d` (a new pinned dependency
  from the same authors). The package measures both on the yardstick map and
  records the choice. 2D colliders (box, circle, capsule, polygon), top-down
  (no gravity) and side view, a 2D character controller.
- **Tilemaps** (a tileset file and a `Tilemap` component in chunks, layers,
  collision built from tiles, y-sorting) with **painting in the editor**
  (brush, rectangle, fill, erase, picker).
- **A pixel-perfect camera**, a fixed viewport, the pointer in the world,
  sorting layers.
- **2D lights and vision**: point lights with occluders built from the
  tilemap's walls; a line-of-sight visibility polygon that game code can ask
  for and that replication uses for "players within vision".
- **The editor's 2D mode**: a top-down orthographic scene view with pan and
  zoom (no orbit), rectangle selection, sprite picking, a tile palette, snap
  to pixel or grid.

## 5. Project kinds

- `wish.json` gets a `kind`, `2d` or `3d`, by addition (a project without it
  is read as `3d`, as every 1.0 project is; files stay byte-identical).
- **New project** on the welcome screen starts with the kind, as Unity's hub
  does: **2D** or **3D**, each with its templates. 2D: Empty 2D, Top-down,
  Platformer, Online party. 3D: Empty 3D, Islands (the showcase),
  Third-person, Online arena. `wen new --kind 2d --template top-down`.
- The kind sets defaults, never limits: the editor opens in 2D mode, the
  Create menu lists sprites and tilemaps first, the default camera is
  orthographic, the physics profile is 2D, the default look suits flat
  sprites. A 2D project can still hold 3D, and the other way round.
- Templates that play online come with a lobby screen and their own
  scenario tests with bots.

## 8. Test plan

- The network simulator is deterministic: same seed, same delivery, same
  hashes. Scenario tests of `examples/station` play 6 to 10 bots over 100 ms
  latency, jitter and 5 % loss and assert the match's result and hash.
- A two-process test on one machine over localhost UDP in CI (Windows and
  Linux), and a relay test (host, relay and clients as processes).
- Hidden information: a test asserts that a player's received bytes never
  contain a component of an entity the player may not see.
- Hostile packets: fuzzing of every message kind against a running host.
- Prediction: with no loss, a client's predicted state equals the host's
  bit for bit; under loss, it converges within a stated number of ticks.
- Every 2D feature: headless tests and golden images, as in M6.
- The scorecard gets 2D and online tasks; an agent must make a small online
  game pass its bot test.
