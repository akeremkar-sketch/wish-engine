## 1. Problem

The yardstick game of release 1.1 is a top-down station of rooms,
corridors, walls, doors and vents. Building it from one entity per wall
tile (the physics note's test map had 298 of them) is slow to make, slow to
change, and unreadable for an agent. Every 2D engine has a tilemap: a grid
of small pictures from a tileset, painted with a brush, with walls that
collide.

What this package must give:

- a **tileset**: tiles cut from a picture by a grid, or taken from a sprite
  sheet, with properties per tile (solid, a collision outline, a name);
- a **tilemap** file: layers of tiles in chunks, of any size, canonical,
  size-capped, a document and an asset everywhere a file kind must be;
- a `Tilemap` component that puts a map in the world;
- **painting** through the control plane (cells, rectangles, flood fill,
  erase; batched, with `dry_run`), written atomically, in one history with
  its actor, undoable; the agent and the editor use the same call;
- **drawing** through the batched sprite path, only what is on screen,
  pixel-exact under an orthographic camera; `describe_view` reports it;
- **collision**: solid tiles merged into few boxes, deterministically, as
  static colliders of the 2D profile; walls stop a top-down character;
- **editor painting**: a palette and brush, rectangle, fill, erase and
  picker tools in the scene view.

## 2. Where tile data lives

Components are fixed-size `Plain` types (invariant 1), and a map is any
size. Options: (a) one entity per tile (what the physics note's test did:
hundreds of entities, a scene file of thousands of lines, a world hash over
data that never moves); (b) tile data in a file of its own that a component
names, as a model or a sheet is named. Decision: **(b)**. The file is the
source of truth (invariant 3); the world holds a `Tilemap` component that
names it and says how it is drawn; what the simulation needs of the file
(collision shapes) is an extension filled when a session starts, as sprite
clips are (ADR-026; 1.1-sprites §3.3).

## 3. The two files

### 3.1 Tileset: `*.tileset.json`, format 1

```json
{
  "format": 1,
  "grid": { "columns": 8, "frame": [16, 16], "rows": 4 },
  "image": "assets/tiles/station.png",
  "tiles": {
    "8": { "name": "wall", "solid": true },
    "9": { "name": "ramp", "shape": [[0, 0], [1, 0], [1, 1]], "solid": true }
  }
}
```

- The tiles are cut **either** from `image` (a PNG) by `grid` (the same
  keys as a sprite sheet's grid: `frame`, `columns`, `rows`, `margin`,
  `spacing`; numbered from 0 left to right, then down) **or** taken from
  `sheet` (a `*.sheet.json`: its frames, in its order, are the tiles; a
  sheet's clips do not animate tiles in this package).
- `tiles` (optional) gives properties by tile number (written without
  leading zeros): `solid` (default false), `shape` (a convex outline of 3
  to 16 points in tile units from the tile's bottom left, `[0, 0]` to
  `[1, 1]`; only for a solid tile; left out: the whole square), `name` (1 to
  64 bytes, for people and agents).
- A reader of its own in `wish_asset::tiles` (the sheet's pattern: every
  mistake a located diagnostic with a hint; `tileset_invalid` for what a
  tileset must say). 256 KiB a file (`tileset_file_too_large`), 4096 tiles.

### 3.2 Tilemap: `*.tilemap.json`, format 1

```json
{
  "format": 1,
  "layers": [
    {
      "chunks": {
        "0,0": [
          [-1, -1, 8, 8, ...16 numbers],
          ...16 rows, the top row first
        ]
      },
      "name": "walls"
    }
  ],
  "tileset": "assets/tiles/station.tileset.json"
}
```

- Cells are whole coordinates (x right, y up) in the map's own plane; cell
  `(x, y)` covers `[x, x + 1) × [y, y + 1)` cells from the map's origin.
- A **chunk** is 16 × 16 cells; its key is `"cx,cy"` (cell `x` is in chunk
  `floor(x / 16)`). It is written as 16 rows of 16 numbers, **the top row
  first**, so the text reads like the picture. `-1` is an empty cell,
  `0` and up a tile of the tileset. The canonical writer puts a row of
  numbers on one line, so a chunk is 16 short lines.
- **Layers** are drawn in their order (later over earlier). A layer has a
  `name` (unique, 1 to 64 bytes) and `collide` (default true: its solid
  tiles are walls; false for decoration).
- Canonical form is the scene files' (`wish_scene::json::to_canonical`);
  chunk keys are written without leading zeros (`-1,0`, never `-01,0`); a
  chunk with no tile is left out; defaults are left out. Load then save is
  byte-identical.
- Limits: 4 MiB a file (`tilemap_file_too_large`, never read whole beyond
  that), 16 layers, 4096 chunks in all (a million cells), chunk keys from
  -4096 to 4095 (cells from -65,536 to 65,535), tile numbers up to 65,535.
  A tile number the tileset lacks is a warning (`tile_not_in_tileset`) and
  draws nothing.

### 3.3 Everywhere a file kind must be

Both are documents and assets (like material files and sheets):
`wish_asset::is_document_asset`, the asset index, `read_document_asset`
with each kind's cap; `check` reads them (and a tilemap's tileset, and the
tileset's picture or sheet); `wen fmt` rewrites them canonical; `wen
migrate` takes format 1 as current; `wen watch` reloads on them; `wen mv`
rewrites the references inside them (a tileset's `image`/`sheet`, a
tilemap's `tileset`) and to them (`Tilemap.map` in scenes and prefabs, a
tilemap's `tileset`); checkpoints keep and restore them; `asset_list`
kinds `tileset` and `tilemap`; `asset_info` reports them; `asset_create`
makes both (a tilemap from its tileset and layer names, with chunks if
given), all or nothing, with `dry_run` and `overwrite`.

## 4. The component

`Tilemap` (`wish_types::tilemap`, registered with the render types, in the
SDK and its prelude):

| Field | Type | Default | Meaning |
|---|---|---|---|
| `map` | AssetRef | none | the `*.tilemap.json` |
| `cell_size` | [f32; 2], m | [1, 1] | the size of one cell in the entity's plane |
| `layer` | i32, -1000 to 1000 | 0 | the sprite layer the map is drawn on (its own layers in file order within it) |
| `color` | Color | white | a tint over every tile |
| `smooth` | bool | false | smooth scaling (false: sharp pixels, no seams) |
| `y_sort` | bool | false | sprites on this layer are drawn by height: lower (smaller y) over higher, and over the map |

The map stands in the entity's XY plane from its origin (cell (0, 0)'s
bottom left corner), scaled and turned by the entity's transform.

`y_sort` is the one sorting setting this package needs (characters in a
top-down room in front of each other); sorting layers as a whole are
package 6.

## 5. Painting through the control plane

### 5.1 The tool: `tilemap_edit` (the 35th)

```json
{ "tilemap": "maps/station.tilemap.json",
  "ops": [
    { "op": "rect", "layer": "walls", "from": [0, 0], "to": [19, 0], "tile": 8 },
    { "op": "set", "layer": "floor", "cells": [[3, 4, 1], [4, 4, 1]] },
    { "op": "fill", "layer": "floor", "at": [5, 5], "tile": 1 },
    { "op": "erase", "layer": "walls", "from": [9, 0], "to": [10, 0] }
  ],
  "reason": "a door in the south wall" }
```

- Operations: `set` (cells `[x, y, tile]`, `-1` erases), `rect` (`from`
  and `to` corners, both included), `fill` (the 4-connected region of cells
  that hold what `at` holds, in that layer, bounded by the map's extent:
  the box of every tile of every layer; at most 65,536 cells,
  `fill_too_large`), `erase` (a rectangle to empty), `add_layer {layer,
  collide?, before?}`, `remove_layer {layer}`, `set_layer {layer, collide?,
  name?}`.
- All or nothing, in order, one revision; at most 65,536 cells changed by
  one call (`paint_too_large`). `dry_run` reports what would change.
  `base_revision` refuses a call made against an older map. A tile number
  the tileset lacks is refused (`unknown_tile`; when the tileset cannot be
  read, nothing is refused and `check` says what is wrong). The answer
  gives the revision, the cells the call changed in the end per layer (a
  cell painted and erased again did not change), their box, and the
  layers as they are now.
- `action: "get"` only looks (not in the activity feed): the layers
  (names, collide, tile counts, the box they cover) and, with `from`/`to`,
  the tiles in that rectangle as rows, top first (at most 64 × 64).
- The file is written in canonical form, atomically, before the call
  answers. A tilemap file a person broke by hand is never overwritten
  (`tilemap_file_invalid`, like a scene's).

### 5.2 One history

Options: put painting into `edit_apply` (the scene's history) or give each
map a history of its own. A stroke changes the map file, not the scene; a
scene's history entry that changes another file would make undo touch two
files and make a map shared by two scenes belong to neither. Decision: a
**history per map file**, kept the way a scene's is (in the workspace, in
memory, `Actor` on every entry, numbered revisions), reached through the
same tool: **`edit_history` takes a tilemap file as its `scene`**: `list`,
`undo`, `redo` and `revert` work on it as on a scene. A map changed on disk
outside the engine enters its history as one change by `file`, as a
scene's does. Every `tilemap_edit` call enters the activity feed with its
actor, its map (as `scene`) and its revision, so a card's *Undo this* takes
a stroke back (`edit_history revert`).

Entries keep the map before and after (chunks are shared, copied on
write, so an entry costs the chunks it changed); undo and redo put one or
the other back; a revert sets the cells the change touched back if no later
change touched them (`revert_conflict` otherwise); a revert of a change
that added or removed a layer is refused. 200 entries per map are kept.

## 6. Drawing

- The renderer is given tilemaps as it is given sheets
  (`Renderer::set_tilemap`: the picture's path, every tile's rectangle, the
  layers' chunks); it never reads a file. The control plane loads the maps a
  scene's `Tilemap`s name, their tilesets (and sheets), and the pictures,
  next to sheets (`render::load_tilemaps`, through `load_ui_pictures`, which
  every picture goes through: tools, editor, `wen capture`/`view`/`play`).
  A map that cannot be used is `tilemap_not_loaded` (nothing is drawn).
- Tiles go through the batched sprite path (1.1-sprites §5): one instance
  per tile, the corners worked out on the CPU from the cell's corners
  (neighbouring tiles share exactly the same corner values: no seams, no
  overlaps), the tile's rectangle of the tileset picture, the tint. One
  picture: one batch for a whole map.
- **Only what is on screen:** a chunk whose four corners project outside
  the picture is skipped; cells are emitted chunk by chunk, layer by layer.
- **Order:** every tile of a map has the map's layer and the distance of
  its entity's origin, so a map sorts as one flat thing, and its layers and
  chunks keep their order (the sort is stable). With `y_sort`, sprites of
  that layer sort by the height of their anchor and come after the map.
- **Pixel-exact:** under an orthographic camera whose pixels fit the cells
  (cell size × pixels per meter whole), with sharp sampling, every tile's
  texels land on whole pixels (a golden image checks it pixel by pixel).
- `describe_view` lists `tilemaps`: each map's entity, file, layer, its box
  in the picture, the cells it shows (`[x0, y0, x1, y1]`) and how many
  tiles are drawn. `describe_view` with `point: [x, y]` (a pixel) also says
  which cell and which tile of each layer are under it (cheap: one inverse
  projection onto the map's plane).

## 7. Collision

- A cell is solid when a colliding layer holds a solid tile there. Full
  solid cells are merged into boxes, **deterministically**: cells are taken
  in order (y up, then x right); each unused solid cell starts a box that
  grows right as far as solid unused cells go, then up as far as the whole
  row below it is matched; its cells are marked used. A room's wall of 60
  cells is a handful of boxes. A solid tile with a `shape` is one convex
  collider of its own (slopes for platformers), in the same order.
- What the simulation needs (the boxes and outlines per map) is an
  extension, `wish_physics::TileShapes`, filled by the control plane when a
  session starts (and when a scene is asked a `physics_query`), from the
  project's maps as they are then. A map painted during a session changes
  the next session (as sheets do).
- Physics makes one fixed body per `Tilemap` entity (entity order) with its
  boxes as cuboids 1 m deep in the map's plane, scaled by the cell size and
  the entity's scale, placed like any fixed body (held to the plane in a 2D
  profile). Collider defaults are `Collider`'s. Contacts and queries name
  the tilemap's entity.
- **Replays:** the shapes are part of what the simulation reads, so they are
  in the replay header's `assets` fingerprint (written only when a project
  has tilemaps, so every existing fingerprint is unchanged).

## 8. Editor painting

With an entity that has a `Tilemap` selected, the inspector shows a
**tile palette** under the component: the layer to paint, the tools
(Brush, Rectangle, Fill, Erase, Picker) and the tileset's tiles as small
pictures. In the scene view, while a tool is on, a press does not pick: the
brush collects the cells it passes over and the rectangle the cells between
press and release; on release the stroke is **one `tilemap_edit` call by
`human`**; fill and the picker act on a click. The cells under the pointer
are outlined. Ctrl+Z while painting undoes the last stroke of that map
(`edit_history` on the map). The editor's 2D mode is package 8: painting
works in today's scene view, best under an orthographic camera.

What else is done by hand: *Assets > New... > Tileset* makes a tileset of
the selected picture (16-pixel tiles, larger when the picture would have
more than 4096) and *New... > Tilemap* a map of the selected (or first)
tileset with a `floor` and a `walls` layer, each one `asset_create` by the
person; *Solid tile* in the palette makes the chosen tile a wall or not
(`asset_create` over the tileset with everything it writes, read again
first). New interface text, in all 11 languages: *Tile palette*, *Paint on
layer*, *Brush*, *Rectangle*, *Fill*, *Erase*, *Picker*, *Solid tile*,
*Tileset*, *Tilemap*, the painting hint and two status lines.

## 10. Not in this package

- A tile's `name` and collision `shape` are written in the tileset file
  (or by `asset_create`); the editor has no fields for them yet (the
  palette sets `solid` only). Animated tiles (a sheet's clips) and
  auto-tiling are not here (auto-tiling is release 1.7's second half).
- A map painted during a session changes the next session, as sheets do;
  game code cannot change tiles at run time (doors are entities).
- No recipe and no scorecard task yet: package 15 writes them with the
  yardstick game.
- Collider settings of tile walls are `Collider`'s defaults (layer, mask,
  friction); a field for them comes when a game needs it.
