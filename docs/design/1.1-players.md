# Release 1.1, package 2: players

**Status:** done, 21 November 2026, on the branch `players` (from `r1.1`).
Plan: [1.1-2d-and-online.md](1.1-2d-and-online.md) §3 and §6, package 2.
Architecture: ADR-029 (online play), ADR-028 (rules of the train), ADR-016
(input as actions).

## 1. Problem

Input is single-player. `input.json` maps keys to actions; every tick
`wish_input::apply` writes the actions' state into the `ActionState`
resource (looked up by a digest of the name), game code reads it through the
SDK's `Actions`, tools inject it with `sim_step`'s `input`, and replays record
it (`replays/<name>.replay.jsonl`: a header, the input changes, the hash of
every tick). Online play (ADR-029) runs one true simulation on the host with
the inputs of every player, so the world, game code, the control plane and
replays must know about more than one player before any networking exists.

Constraints:

- A single-player game keeps working unchanged: game modules built with the
  1.0 SDK still load, its scenes, tests and `input.json` stay byte-identical,
  and the answers of the tools to single-player calls stay the same bytes.
- ADR-028 rule 5: formats change by addition. Rule 2: a replay carries the
  engine version (and the executor id).
- Game code stays cheap and bounded at the guest boundary, and never sees a
  device or a socket.

## 2. Options

**Where every player's actions live.**

1. *A player entity each* (`Player` + an input component). Natural for ECS and
   for per-player visibility later, but a single-player session would either
   have no player entity (the same code does not run alone) or gain one (its
   entity count, queries and tool answers change). Rejected.
2. *Change `ActionState` to hold every player.* Its layout is part of the ABI:
   every game module built with 1.0 declares the old layout and would be
   refused. Rejected.
3. *`ActionState` stays player 0's; a new resource holds every player's.*
   Chosen. Two sub-options for single-player worlds:
   - (a) always write the new resource, with only player 0 in it: one code
     path, but every single-player world gains an 8 KiB resource;
   - (b) write it only when the session has more than one player: a
     single-player world gains nothing; the SDK parameter that reads it must
     then also read `ActionState`, so that player 0 is right when the new
     resource is absent. **Chosen**: pay for what you use.

**How game code reads it.** `Actions` stays exactly as it is (one frame
section, player 0), so single-player systems cost what they cost. A new SDK
parameter, `PlayerActions`, reads three resources; the SDK's `SystemParam`
trait gains two provided methods (`describe_into`, `fetch_from`) that let a
parameter take several frame sections. The host is unchanged: it sees three
ordinary read-only `res` entries. This is an addition to the SDK (no item
removed or changed in meaning) and not an ABI change.

**Replay format.** (a) always write format 2; (b) format 2 only with more than
one player. **Chosen: (b)**, as the plan says. A single-player replay stays
format 1, so a 1.0 engine still reads it; a multi-player replay is format 2, so
a 1.0 engine refuses it ("a format the engine does not read") instead of
silently playing player 1's input as player 0's.

## 3. Decision

**World** (`wish_types::input`, registered by `wish_input::register`):

- `Players { count }` (1 to 16, default 1). Written only when a session has
  more than one player; a world without it has one player, which is the
  default `Res<Players>` gets. Player ids are 0 to `count - 1`; `PlayerId` is
  a `u32` (a type alias, so a game's component field `player: PlayerId` reads
  as a plain number in scene files).
- `PlayerActionState { players: [PlayerActionSlots; 16] }`, each entry the
  same 32 slots as `ActionState`. Written only with more than one player;
  entry 0 then equals `ActionState`, entries beyond the session are at rest.
  8 KiB.
- `ActionState` is unchanged and stays player 0's.
- `wish_input::set_players(world, n)` (at session start) and
  `wish_input::apply_players(world, map, inputs)` (every tick). With one
  player, `apply_players` is exactly `apply`; the pointer is player 0's only
  (it is this machine's interface). `MAX_PLAYERS` = 16 (the plan's yardstick
  game has 4 to 10).

**Game code** (`wish_sdk`): `PlayerActions` with `count()`, `ids()` and
`of(id) -> Actions` (an id not in the session reads as at rest), and
`Players`, `PlayerId`, `PlayerActionState`, `PlayerActionSlots`,
`MAX_PLAYERS` re-exported (the first three in the prelude). A system that asks
for `PlayerActions` receives about 8.5 KiB per call, fixed by `MAX_PLAYERS`
and `MAX_ACTIONS`. Alone, `PlayerActions` has one player, 0, read from
`ActionState`, so the same code runs single-player, as a host and later as a
client.

**Control plane** (all by addition; the old forms mean player 0):

- `sim_start` `players` (1 to 16, default 1). The answer says `players` only
  when there are several, so single-player answers are the same bytes.
- `sim_step` `players`: `{ "1": { "move": [1, 0] } }`, each player's input
  written like `input`; `input` stays player 0's. Players not named are at
  rest for the call. An id the session does not have is `unknown_player`;
  player 0 given twice, or a pointer for another player, is
  `invalid_parameter`. `until` needs nothing new: it stops the same run.
- Scenario tests: a top-level `"players": N` and a run step's `"players"`
  object, the same shape as `sim_step`'s.
- Forks (`sim_restore` `fork`) keep the player count.

**Replays** (`wish_control::replays`):

- The header of every new replay carries `engine` (the engine version) and
  `executor` (`wish_script::EXECUTOR`, `"wasmtime"`): ADR-028 rule 2, by
  addition to format 1 (a 1.0 engine reads header keys by name and ignores
  the others).
- With more than one player: `"format": 2`, `"players": N`, and every input
  line says `"player": p`. Input lines are written per player when that
  player's input changes, in tick order and player order within a tick.
- Playback starts a session with the replay's players and feeds each player's
  input. It says when the engine version or the executor differs from the
  recording's, or when the replay does not say (recorded before 1.1):
  warnings `replay_engine_changed` and `replay_executor_changed`.
- Format 1 files written by 1.0 are read as before. Note: every engine type a
  package adds moves the world hash of every world (the registry fingerprint,
  M12 render foundation §6), so a replay *recorded by 1.0* diverges at its
  first tick under 1.1 whatever this package does (other 1.1 packages add
  types too); ADR-028 rule 3 allows that in a minor version, and playback
  says why. What holds bit for bit is everything recorded and played by one
  engine: single-player replays in format 1, multi-player ones in format 2,
  and the format-1 files of 1.0 still parse and play.

**Recorded hashes.** Registering `Players` and `PlayerActionState` moves the
world hash of every world that registers the engine's types (the registry
fingerprint). No recorded hash in the repository covers those worlds
(`wish_core`, `wish_ecs` and `wish_physics` record hashes of their own type
sets), so none changed.

**Defaults.** The two new resources are engine types, so their defaults are
recorded in `crates/wish_scene/src/defaults/format-2.json`
(`UPDATE_DEFAULTS=1 cargo test -p wish_control --test look_lock`);
`format-1.json` is not touched.

## 4. Test plan

- `wish_input/tests/input.rs`: one player through `apply_players` gives the
  same world hash as `apply` and writes no new resource; three players get
  their own values and their own pressed/released edges; player 0's entry
  equals `ActionState`; 17 players are refused.
- `wish_control/tests/players.rs` (builds game code; needs the SDK pack):
  - game code moves each player's avatar from `PlayerActions.of(player)`;
    two players move independently in a scenario test (`tests/*.test.json`
    with `"players": 2`), and through `sim_step` `players`;
  - a two-player replay records format 2 with per-player lines and the
    engine version, and plays back bit for bit;
  - a single-player replay is format 1, plays back, and a 1.0-shaped file
    (format 1, no `engine`) still plays bit for bit, with the note that it
    does not say its engine;
  - mistakes: an unknown player, player 0 given twice, the pointer for
    another player, a format-2 file whose input names a player it does not
    have.
- `wish_cli/tests/parity.rs`: a two-player session, its input and an
  unknown player in the in-process / `wen do` / MCP comparison, and a
  two-player recorded and replayed run in the two-process comparison (same
  answer bytes, the replay header's engine version included).

## 5. Not done here

- Joining and leaving during a match (a `Players` field for players who left,
  by addition) belongs to the lobby package (12).
- `wen play` and the editor's Play stay single-player; "Play with N players"
  is package 14.
- Player-tagged input from the network, prediction and replication are
  packages 9 to 11.
