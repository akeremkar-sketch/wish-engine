# Release 1.1: the network transport (`wish_net`)

Package 9 of [1.1-2d-and-online.md](1.1-2d-and-online.md) §6, first part:
the transport, its encryption, local discovery and the deterministic network
simulator. Architecture: ADR-029 in [../DECISIONS.md](../DECISIONS.md).
Replication, prediction, the lobby and `wen relay` are later packages and
build on what is here.

Recommended model and effort: Opus 5.5, high (a foundation package of a new
area; one reviewer, the user's rule for non-foundation packages does not
apply).

Status: built on 21 November 2026 on the branch `net-transport` (from
`r1.1`); the tests of §5 pass (`cargo test -p wish_net`: 21 unit tests, 7
hostile, 14 simulated, 3 over localhost UDP). Discovery by real broadcast is
not tested in CI (firewalls); its query is tested by sending to `127.0.0.1`
and by broadcast in the simulator. Not yet run on Linux.

## 1. Problem

Online play needs a way for a host and its players to exchange bytes over the
internet and the local network. The engine has none. What the later packages
need from it:

- **Two channels.** State goes unreliably (a lost snapshot is replaced by the
  next one); messages, joins and inputs that must arrive go reliably and in
  order.
- **Messages larger than a datagram** (a full snapshot when a player joins),
  so fragmentation and reassembly.
- **A room code** that a player types to join, checked by the host.
- **Privacy and integrity.** A player on the same café network must not read
  the traffic of a match or inject packets into it.
- **A hostile peer cannot crash or freeze the host** (invariant 7 applied to
  the network, ADR-022 as amended by ADR-029).
- **Testable without people and without the wall clock.** The same endpoints
  must run over a simulated network whose latency, jitter, loss, duplication
  and reordering come from a seed, stepped by ticks, so a test of ten bots
  over a bad network gives the same bytes every time (determinism, ADR-029).
- **Local discovery**: the games on the local network, without typing an
  address.

## 2. Options

| Option | For | Against |
|---|---|---|
| An existing game networking crate (renet, laminar, naia, GGRS) | Less code | Each brings its own transport or async runtime and its own idea of time (most read `Instant` inside); none runs over a seeded simulator stepped by ticks; replication must be schema-driven anyway (ADR-029, "Alternatives"). |
| QUIC (quinn) | Reviewed, congestion control, TLS 1.3 | Large (tokio, rustls, ring or aws-lc), reads the wall clock, cannot be stepped by a simulator. Can replace the transport later behind `wish_net` (ADR-029). |
| DTLS | Standard | No maintained pure-Rust implementation under a permissive licence. |
| **A small protocol of our own** over `std::net::UdpSocket`, with reviewed primitives for the cryptography | Small, no runtime, time passed in by the caller, runs over the simulator unchanged | We own the protocol's correctness: it is kept small and fuzzed. |

For the cryptography: **RustCrypto `chacha20poly1305`** (AEAD, Apache-2.0 OR
MIT; `chacha20` is already in the tree) and **`x25519-dalek`** (key exchange,
BSD-3-Clause), both audited and widely used. Key derivation is SHA-256 with
domain separation (`sha2`, already in the tree). OS randomness through
`getrandom` (already in the tree). No `ring`/`aws-lc` (C and assembly, large).

## 3. Decision

The crate `crates/wish_net` depends on `wish_core` only (plus the libraries
above). It has five parts:

- `transport`: the `Transport` trait (`local_addr`, `send`, `recv`, all
  non-blocking). `UdpTransport` wraps a non-blocking `UdpSocket`;
  `SimTransport` is a node of a `SimNetwork`.
- `wire`: the packet layout and the frames inside a data packet, as pure
  encode/decode functions (the relay will read headers with the same code).
- `crypto`: key exchange, key derivation, sealing and opening, and `Entropy`
  (where secrets come from).
- `endpoint`: `Endpoint<T: Transport>`, one type for a host (many peers) and a
  client (one host): handshake, channels, fragmentation, acknowledgements,
  resends, limits, timeouts, events.
- `discovery`: a responder that answers broadcast queries and a query that
  collects answers.

### 3.1 Time

No part of `wish_net` reads the clock. `Endpoint::update(now_ms)` takes a
monotonic time in milliseconds from the caller: over real UDP the caller
passes the time since it started (an `Instant`, outside the crate); over the
simulator it passes `SimNetwork::now_ms()`, which is `tick × tick_ms`.
Resends, timeouts, keepalives, rate limits and cookie lifetimes all use that
number, so a simulated run is a pure function of its seed and its inputs.

### 3.2 Packets

Every datagram starts with a plain four-byte header: `W N`, the protocol
version (1) and the packet kind. A datagram is at most **1200 bytes**
(`MAX_PACKET`, safe under every common path MTU); anything larger is
dropped without being read.

| Kind | Direction | Body | Sealed |
|---|---|---|---|
| `Hello` | client → host | client public key, client token (16 random bytes), cookie (zero the first time), padding to 256 bytes | no |
| `Challenge` | host → client | client token, cookie, host public key | no |
| `Connect` | client → host | client public key, client token, cookie, sealed room code | the room code |
| `Reject` | host → client | client token, reason | no |
| `Data` | both | connection id, packet number, frames | yes |

The handshake is stateless on the host until the client proves it can
receive at its address (the cookie, as in DTLS's HelloVerify): `Hello` is
padded so that `Challenge` is smaller than what it answers (no
amplification), and the host does no key exchange and keeps no state before
a `Connect` with a valid cookie. The cookie is
`SHA-256(secret, time bucket, address, client key, token)`, valid for the
current and the previous five-second bucket. `Challenge` and `Reject` echo
the client's token, so a third party off the path cannot forge them.

Keys: the host has one X25519 key pair per hosted match; the client a fresh
one per connection attempt. Both sides compute
`shared = X25519(client, host)` and derive two keys, one per direction,
`SHA-256("wish-net/1 key c2h" | shared | client public | host public)` and
the same with `h2c`. A shared secret of low order (a malicious public key)
is refused. The `Connect` carries the room code sealed with the client's
key, so a listener on the network does not see it. The host compares it and
answers either with a `Data` packet holding a `Welcome` frame (the peer id)
or with a `Reject`. A lost `Welcome` is sent again when the client repeats
its `Connect` with the same key.

`Data` packets are sealed with ChaCha20-Poly1305: the nonce is the packet
number (a 64-bit counter per direction, never reused), the header is the
associated data. The receiver keeps a 128-packet replay window: a packet
seen before, or older than the window, is dropped. A packet that does not
open is dropped and counted; it never ends a connection (otherwise anyone
could end one with a forged packet).

Frames inside a `Data` packet: `Welcome`, `Ack`, `Reliable` and `Unreliable`
fragments, `Ping`, `Pong` and `Disconnect`. Any frame that does not parse, or
a fragment that breaks a limit, ends the connection with
`net_protocol_violation`: only a peer that has the keys can send frames, so
it is that peer misbehaving.

### 3.3 Channels

- **Reliable, ordered.** A message is cut into fragments of at most 1024
  bytes, each with a reliable sequence number, its index and the fragment
  count. The receiver acknowledges with the next sequence it expects (every
  one below has arrived) and a 64-bit mask of the ones after it. The sender
  sends again what is not acknowledged after the retransmission timeout
  (`1.5 × smoothed round trip + 25 ms`, between 50 ms and 2 s, doubled per
  resend of the same fragment). At most 256 fragments are in flight; the rest
  wait in a queue of at most `max_queued_bytes` (`net_send_queue_full`
  beyond). The receiver keeps out-of-order fragments within a window of 512
  ahead of what it expects and delivers whole messages in order.
- **Unreliable.** A message is cut into fragments with a message id; a whole
  message is delivered once, a partial one is forgotten after a second or
  when eight newer ones are waiting. A duplicate is dropped.

The round trip comes from `Ping`/`Pong` (the sender's own time, echoed),
sent every `keepalive_ms`. A peer silent for `timeout_ms` is disconnected
with `net_timed_out`.

### 3.4 Limits (a hostile peer)

| Limit | Default | Beyond it |
|---|---|---|
| Datagram size | 1200 bytes | dropped, counted |
| Datagrams read per `update` | 4096 | the rest wait for the next update (no freeze) |
| Datagrams per second per peer | 1000 | dropped, counted |
| Handshake packets per second (all unknown addresses) | 256 | dropped, counted |
| Key exchanges per second | 64 | dropped, counted |
| Message size | 64 KiB (at most 1 MiB) | a send is refused with `net_message_too_large`; a received fragment count above it is a protocol violation |
| Peers | 16 (at most 256) | `Reject` with `room_full` |
| Reliable receive window | 512 fragments | fragments beyond it are dropped (the sender sends them again) |
| Partial unreliable messages | 8 per peer | the oldest is forgotten |

### 3.5 The simulator

`SimNetwork::new(seed, tick_ms)` with `LinkConditions` (latency, jitter,
loss, duplication, reordering) for every link or per directed link. A sent
datagram draws, from the network's one `wish_core::Rng`, whether it is lost,
whether it is duplicated, its jitter and whether it is held back (reordered);
it is delivered at the first tick at or after its arrival time. Datagrams
due in the same tick are delivered in the order they were sent. Broadcast
(`255.255.255.255`) reaches every node bound to that port. Nothing depends
on hash order or threads; the network keeps a `StableHasher` of every
delivery (tick, from, to, bytes), so a test can compare two runs by one
number. `inject` puts a datagram on the wire with any source address (an
attacker who spoofs), for the hostile tests.

### 3.6 Discovery

A host runs a `DiscoveryResponder` on the discovery port (47 610 by default).
A client's `DiscoveryQuery` sends a `Query` (a 16-byte nonce and the game's
id) to the broadcast address, or to any address it is given, and collects
`Announce` answers: the match's name, the game id, the game port, players and
the maximum, the host's public key (so a client can pin it when it joins) and,
only if the host chose it, the room code. Both are plain, bounded and fuzzed;
the responder answers at most 32 queries a second.

### 3.7 What 1.1 does not protect against

The handshake has no long-term host identity: without a pinned host key
(from discovery, or given by hand), an active attacker on the path who
terminates both sides can read the traffic. A room code is short, so such an
attacker can also guess it offline from one `Connect`. Plain `Reject`s are
not authenticated beyond the client token. No congestion control beyond the
in-flight window. These are stated in the public text with the preview label
(ADR-028 rule 1); a password-authenticated key exchange can replace the
handshake behind the same API.

## 5. Test plan

- `crypto`: a sealed packet opens; a flipped bit anywhere (header, body, tag)
  does not; the wrong key does not; a low-order public key is refused.
- `wire`: every packet kind and frame round-trips; random bytes, truncations
  and extensions never panic (property loops with `wish_core::Rng`).
- Simulator: same seed, same delivery hash; different seed, different hash;
  loss, duplication and reordering happen at about the asked rates.
- Endpoint over the simulator: 1000 reliable messages from 1 byte to 10 KiB,
  both ways, under 100 ms latency, 30 ms jitter, 5 % loss, 2 % duplication and
  10 % reordering arrive complete and in order; unreliable messages arrive at
  most once and whole; the same run twice gives the same delivery hash and
  the same received bytes.
- Handshake: wrong room code, full room, pinned key mismatch, connect
  timeout, peer timeout, disconnect.
- Localhost UDP: a host and a client exchange reliable and unreliable
  messages over `127.0.0.1`; discovery answers a query sent to `127.0.0.1`.
- Hostile peers: a tampered captured packet and a replayed one are dropped
  and the connection goes on; a fuzz run sends mutated packets of every kind
  (bit flips, truncation, extension, random bytes, wrong version, wrong key,
  spoofed source) and, through a hand-made client that holds real keys,
  random sealed frames. No panic; the host stays responsive and a real
  client still talks to it afterwards; a flood is bounded per update.
