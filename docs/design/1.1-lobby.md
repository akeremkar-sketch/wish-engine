Plan: [1.1-2d-and-online.md](1.1-2d-and-online.md) §3 and §6, package 12.

crate is `wish_lobby`; its tests are listed in §9 and pass

## 1. Problem

Replication sends each player the state it may see, and inputs come back.
A hidden-role party game needs three more things before it can be played:

- **Messages.** A meeting has chat and votes; a task tells the host it is
  done; the host tells one player a secret ("you are a saboteur", "your
  partner is Ada") and tells everyone that a meeting was called. These are
  events, not state: they happen once, in order, and must not be lost.
  Game code declares them with the engine's schema macros and sends them
  with a target. A message to one player must never reach another.
- **A lobby.** A room code, players joining and leaving, names and colours
  (two players asking for the same one get different ones, decided by the
  host the same way every time), a ready flag, the host starting the match,
  secret roles dealt by the host from its seed and sent only to their
  owners, the match ending and everyone returning to the lobby.
- **Sessions.** A player whose connection drops comes back into the same
  seat within a grace period; the host leaving ends the match cleanly for
  everyone.

And all of it under the network rules: everything the host's simulation
receives from the network enters at a tick boundary and is **recorded**, so
the host's log replays the match bit for bit (ADR-029); game code never
opens a socket (ADR-011, ADR-022 as amended); a hostile client can neither
crash, freeze nor impersonate (invariant 7 applied to the network); every
limit a client could push is a budget.

## 2. Options

**How game code declares a message.**

1. *A wrapper type per message* (`NetSend<Vote>`, `NetReceived<Vote>`), as
   the task's sketch has it. The schema macros do not take generic types
   (an engine rule: every type that enters a world is declared once, by
   name, with `#[event]`), so the wrapper would need a hand-written `Plain`
   (forbidden) or a second, engine-made type per message whose name the
   game module never declared. Rejected.
2. *A separate list of message types in the configuration*, like the
   replicated components. Two places to keep in step, and the type still
   needs somewhere to say who sent it. Rejected.
3. *An envelope field.* **Chosen:** an event type is a network message when
   it has a field named `net` of the engine's schema type `Net`:

   ```rust
   #[event]
   pub struct Vote {
       /// Where it goes and who sent it (the engine fills `from`).
       pub net: Net,
       /// The player voted for.
       pub choice: PlayerId,
   }
   ```

   The envelope is part of the schema, so `schema_get` and agents see it,
   the JSON of the event shows it, and the engine finds it by the schema in
   every world (the field may be anywhere in the type). Nothing else is
   declared anywhere.

**What a received message looks like.** An ordinary event of the same type,
delivered into the world at a tick boundary with `net.delivered = true` and
`net.from` = the sending player, written by the engine from the connection
it came on and never from the sender's bytes. The game's own outgoing copy
(`delivered = false`) is also in the sender's world (that is how ECS events
work), so a reader asks for delivered ones. The SDK hides the flag:

```rust
#[system]
fn tally(votes: NetReader<Vote>, mut out: NetWriter<VoteResult>, mut board: ResMut<Board>) {
    for vote in votes.read() {          // delivered ones only
        board.votes[vote.net.from as usize] = vote.choice;
    }
    out.to_everyone(VoteResult { ejected: 3, ..Default::default() });
}
```

`NetWriter<E>` (`to_host`, `to_player`, `to_everyone`, `to_group`) and
`NetReader<E>` are SDK parameters built on the existing `send` and `events`
frame entries: **no ABI change**, no new import, and a module built with
the 1.0 SDK still loads. Native systems use `Net::to_host()` and friends on
the envelope and read `World::events_since`.

**Who may send to whom.**

1. *Any player to any player, routed by the host.* Chat between living and
   dead players, spam and whispers that the host's rules never see.
2. *Players send only to the host; the host sends to one player, a group or
   everyone.* **Chosen.** It is the authoritative model of ADR-029 applied
   to messages: a dead player's chat reaches the living only if the host's
   game code passes it on. The same game code still runs everywhere: on the
   host, a message to the host from the host's own player is delivered
   locally, as is the host's own share of a message to everyone or to a
   group. A client's message with another target is not sent
   (`net_message_target_refused`, with the hint to let the host pass it
   on); a hostile client's bytes cannot change that, since the host takes
   every client message as addressed to itself.

**Where the code lives.** `wish_replicate` owns message kinds 0 to 63 and
passes the rest back; the lobby needs the replication host (to admit a peer
under the seat the lobby chose, to resolve network ids in messages) and the
replication client (to map them back). **Chosen:** a new crate,
`wish_lobby`, above `wish_replicate`, knowing `wish_core`, `wish_ecs`,
`wish_schema`, `wish_net`, `wish_types` and `wish_replicate`, and nothing
else of the engine. Its wire kinds are 64 to 95.

**How the host's log replays the match.** The world hash covers change
ticks, so a log of resulting values is not enough: the replay must make the
same writes at the same moments. **Chosen:** every tick boundary is built
in two steps on the host. First the session works out a `TickRecord` (pure
data: the players' input frames for the tick, the host's own actions, the
player count, the lobby's new value, the local player's, the roles, every
delivered message as world-independent values) without writing anything;
then one function, `apply`, writes it into the world. The live host and the
replay call the same `apply` with the same record, so they make the same
writes in the same order. The replication host was changed to work out
inputs without writing them (`Host::take_inputs`); `Host::apply_inputs`
stays, built on it.

## 3. Decision

### 3.1 World types (`wish_types::lobby`, registered by `wish_lobby::register`)

| Type | Kind | Meaning |
|---|---|---|
| `Net { to, player, groups, from, delivered }` | schema struct | The envelope of a network message. |
| `NetTo` | enum | `Host`, `Player`, `Everyone`, `Group`. |
| `Lobby { phase, round, outcome, closed, room, seats: [Seat; 16] }` | resource | The lobby as everyone sees it (public). |
| `Seat { taken, connected, ready, left, color, name }` | schema struct | One player's seat. |
| `LobbyPhase` | enum | `Offline`, `Open`, `Running`, `Ended`, `Closed`. |
| `LobbyClosed` | enum | `None`, `HostLeft`, `Refused`, `Lost`, `Left`. |
| `LocalPlayer { player, joined, host, role, role_name }` | resource | Who this machine is, and its own role (secret). |
| `MatchRoles { roles: [u32; 16] }` | resource | Every player's role. **Written on the host only.** |
| `LobbyRequest { action, value, text }` | event | Game code asks the lobby for something. |
| `LobbyAction` | enum | `Ready`, `NotReady`, `Name`, `Color`, `Start`, `End`, `Reopen`, `Leave`. |

All are in the SDK's prelude. Resources are never replicated, so
`MatchRoles` never leaves the host, and `LocalPlayer` is written on each
machine from what was sent to that machine only.

Game code drives the lobby with `LobbyRequest` (a lobby screen's buttons):
on a client, `Ready`, `NotReady`, `Name`, `Color` and `Leave` go to the
host; `Start`, `End` and `Reopen` are the host's (`lobby_not_host` on a
client). Native callers (the editor, `wen play`, tests) use the same
requests through `HostSession`/`ClientSession` methods.

### 3.2 Lobby states

```
            start (all ready)            end(outcome)
  Open ───────────────────────► Running ─────────────► Ended
   ▲                                                     │
   └──────────────────────── reopen ◄────────────────────┘
  any phase ── host closes ──► Closed (every client: closed = HostLeft)
```

- **Open.** Peers connect with the room code (the transport checks it) and
  send `Join` (name, colour wish, rejoin token or none). The host gives each
  the lowest free seat from 1 (seat 0 is the host's own player when the host
  plays), sends it `Admitted` (its seat, a fresh 16-byte rejoin token from
  the host's entropy, the table of message types with schema fingerprints)
  and admits the peer to replication under that player id. Players set
  names, colours and the ready flag. A player who leaves frees the seat.
- **Running.** `start` needs at least `min_players` seated, every connected
  seated player ready (the host's own seat counts as ready when it starts).
  The round number goes up, roles are dealt (§3.4), ready flags stay. New
  players are refused (`lobby_match_running`). A player who drops keeps the
  seat for `rejoin_grace_ticks` (`connected = false`) and may come back with
  its token into the same seat and player id, with its name, colour and
  role; after the grace the seat is `left` and the token no longer works.
- **Ended.** `end(outcome)` stops the match; the outcome is a number the
  game chooses (who won). Players stay; nobody new joins.
- **Reopen** returns to Open: seats of players who left or are disconnected
  are freed, ready flags and roles are cleared.
- **Closed.** The host closes: every client gets `Closing` on the reliable
  channel, the host keeps its endpoint running until every queue is sent or
  `close_flush_ticks` pass, then closes it. A client whose host goes silent
  (timeout) closes too, with `closed = Lost`; a refused one with `Refused`.

**Names and colours.** A name is cleaned (control characters removed,
spaces trimmed, at most 24 characters and 64 bytes; empty becomes
"Player N"). Two names that are equal ignoring case get the lowest free
suffix " 2", " 3"... A colour is an index below `colors` (default 16); a
wish that is taken gets the next free index upwards (wrapping), or the wish
itself if every colour is taken. Requests are resolved per boundary in seat
order, then in the order each player sent them, so the same requests always
give the same lobby; an earlier seat keeps what it had.

### 3.3 Messages

A message type is any registered event type with a field `net: Net`
(found by the schema; a field called `net` of another type does not count).
At session creation the host lists them by name (at most 64) with their
schema fingerprints; `Admitted` carries the table; a client whose type
differs refuses that type (`net_types_mismatch`).

- **Sending** (after the systems run, `end_tick`): every event of a message
  type in the world with `delivered = false`, sent since the tick began, in
  the world's order. On the host: to the host itself (delivered locally at
  the next boundary, from player 0), to one player, to everyone (every
  connected seated player, the host's own player included when it plays),
  or to a group (`NetGroups` bits). On a client: to the host only.
- **Encoding** (kinds 68 and 83): the type index and the value leaf by leaf
  as replication encodes components (texts as strings, entity references as
  the receiver's network ids: a client names only what it was sent, the
  host resolves it with `Host::resolve` and sends a host entity only to a
  player who may see it, otherwise "none"). All on the reliable channel.
- **Delivering** (at the next boundary, `begin_tick`): as events of the same
  type with `delivered = true` and `from` stamped by the receiver: on the
  host, the seat of the connection it came on; on a client, 0 (every message
  a client receives comes from the host). A client's `to`, `player` and
  `groups` are overwritten with "to the host".
- **Order:** per boundary, by sender (the host's own player first, then
  seats ascending), then in the order that sender sent them. A message
  arriving between two boundaries is delivered at the next one; the
  boundary it entered at is in the log.

A client that predicts runs its systems again on a correction; its
`end_tick` takes the predicted tick and remembers how many messages of each
type it already sent for that tick, so a replayed tick does not send them
twice (wired into `Predictor::frame_with` by `ClientSession::predict`,
package 14b: [1.1-net-tool.md](1.1-net-tool.md) §12).

### 3.4 Roles

`LobbyConfig::roles` lists roles by name; role 0 is everyone else's, and
each later role has a count. At `start`, the seated connected players
(ascending) are shuffled with `wish_core::Rng` seeded from the host's
secret `seed` and the round (Fisher–Yates with `below`); the first
`count(1)` get role 1, the next `count(2)` role 2, and so on; the rest role
0. `MatchRoles` holds every role on the host; each player is sent **only
its own** (`Role`, kind 82: round, role, role name) and writes it into
`LocalPlayer`. The seed never leaves the host, so no client can deal the
roles itself. Game code on the host knows everything (it reads
`MatchRoles`) and tells saboteurs about each other with messages if the
game wants that.

### 3.5 A host tick

```rust
endpoint.update(now);
let mark = session.begin_tick(app.world_mut(), &mut endpoint, tick, &host_actions)?;
app.step()?;                         // the game's systems, tick `tick`
session.end_tick(app.world_mut(), &mut endpoint, mark)?;
endpoint.update(now);
```

`begin_tick` takes every endpoint event: replication messages go to the
replication host, connections and lobby messages to the lobby; then it
builds the tick's `TickRecord` and applies it (§2): player count, the host's
own actions (`ActionState`, written with the same cleaning and edges as the
players'), every player's input frame (`PlayerActionState`), the lobby, the
local player, the roles, the delivered messages; then it advances the
world's change tick once, so the mark separates what entered at the
boundary from what the systems send. The record goes into the match log.
`end_tick` reads the game's outgoing messages and lobby requests sent since
the mark, routes and sends them, sends the lobby to everyone when it
changed, and the replication state of the tick (`Host::send`).

### 3.6 A client tick

```rust
endpoint.update(now);
let mark = session.begin_tick(world, &mut endpoint)?;  // mirror, lobby, messages
// the client's systems
session.end_tick(world, &mut endpoint, mark, tick)?;   // outgoing to the host
```

The client sends `Join` when its connection is accepted. For a rejoin the
caller makes a new endpoint and calls `ClientSession::rejoin(world)`: the
replication mirror is cleared (its entities despawned; the host sends a
fresh snapshot), the token and profile are kept.

### 3.7 What is recorded (the match log)

`MatchLog` is the host's input log: one `TickRecord` per tick that had
anything (ticks with nothing are not stored). A record holds the tick, the
host's actions, every connected player's frame in force, the player count,
and the new values of `Lobby`, `LocalPlayer` and `MatchRoles` when they
changed, and every delivered message (type name, sender, value with texts
as strings and references as the host's entity bits). Replaying is
`apply(world, record)` before each step of a fresh host app built the same
way: the world hash matches the live host's at every tick. `MatchLog` has a
versioned binary form (`to_bytes`/`from_bytes`, decoding bounded and
fuzzed); package 14 puts it into the replay files next to the format-2
input lines.

### 3.8 Seams for the `net` tool (package 14)

`HostSession::status()` and `ClientSession::status()` return plain data
(phase, round, the tick, seats with their peers, names, colours, ready and
connected flags, joins, rejoins, refusals and counts of messages sent,
delivered and dropped by reason); `take_diagnostics()` the diagnostics
(replication's included); `HostSession::log()` the match log;
`replication()` the replication host or client. The tool reads these;
nothing here formats JSON.

## 4. Wire format (kinds 64 to 95, all reliable)

Integers as in replication: `varint` is unsigned LEB128; strings are a
varint length and UTF-8.

Client → host:

| Kind | Name | Body |
|---|---|---|
| 64 | `Join` | u8 version (1), u8 has token, [16] token if so, string name (≤ 64 bytes), u8 colour wish |
| 65 | `Profile` | string name, u8 colour |
| 66 | `Ready` | u8 ready (0 or 1) |
| 67 | `Leave` | — |
| 68 | `Message` | varint type index, every leaf of the value |

Host → client:

| Kind | Name | Body |
|---|---|---|
| 80 | `Admitted` | u8 version, varint seat, [16] token, varint type count (≤ 64), per type: string name, [16] fingerprint |
| 81 | `LobbyState` | u8 phase, varint round, varint outcome, string room, 16 × (u8 flags: taken, connected, ready, left; u8 colour; string name) |
| 82 | `Role` | varint round, varint role, string role name |
| 83 | `Message` | varint type index, varint host tick, every leaf of the value |
| 84 | `Refused` | u8 reason (1 full, 2 running, 3 rejoin expired, 4 version) |
| 85 | `Closing` | — |

A message of a kind that belongs to the other direction, or that does not
parse, is dropped (`net_message_invalid`).

## 5. Budgets (a hostile client)

| Limit | Default | Beyond it |
|---|---|---|
| A client's lobby or game message | `message_bytes`, 1024 bytes | dropped, `net_message_oversized` |
| Messages per player (game and lobby together) | `messages_per_second` 30 sustained, `message_burst` 60 (a token bucket counted in ticks) | dropped, `net_message_flood` |
| Messages delivered per boundary, all players | 1024 (15 players' full buckets are 900) | the rest wait for the next boundary, in order |
| Time to send `Join` after connecting | `join_timeout_ticks`, 600 | disconnected, `lobby_join_timeout` |
| Anything before `Join` but `Join`; a second `Join` | — | dropped, `net_message_invalid` |
| Message types | 64 | the rest are not network messages (a warning at creation) |
| A name | 24 characters, 64 bytes | cut |
| Diagnostics kept | 256 | the oldest are dropped and counted |

The sender of a message is never read from its bytes: `from` comes from the
connection. Every check runs before anything is stored; nothing a client
sends can make the host keep more than these bounds.

## 6. Diagnostics

New: `net_message_oversized`, `net_message_flood`,
`net_message_target_refused`, `lobby_not_ready`, `lobby_full`,
`lobby_match_running`, `lobby_join_timeout`, `lobby_not_host`,
`lobby_wrong_phase`, `lobby_refused`, `lobby_host_left`,
`lobby_rejoin_expired`. Reused: `net_message_invalid`, `net_types_mismatch`,
`net_config_invalid`. Each is in `wish_control::docs::DIAGNOSTICS`.

## 7. Recorded values

The new engine types (`Lobby`, `LocalPlayer`, `MatchRoles`, `LobbyRequest`
and the schema types inside them) are registered with the engine's types,
which moves the world hash of every world that registers them (the registry
fingerprint), as every added engine type does; no recorded hash in the
repository covers such a world. Their defaults are recorded in
`crates/wish_scene/src/defaults/format-2.json` (`UPDATE_DEFAULTS=1 cargo
test -p wish_control --test look_lock`); `format-1.json` is untouched.

## 9. Tests

`cargo test -p wish_lobby`: a host app and up to six client apps over a
`SimNetwork` in one process (`tests/common`). The test game is a meeting:
the host calls it, players chat (`ChatSay` to the host, relayed as
`ChatLine` to everyone), vote (`Vote` to the host), and the host announces
the result (`VoteResult` to everyone) and whispers to each saboteur its
partner (`Whisper` to one player).

- **A six-player lobby** (`tests/lobby.rs`): the host and five clients join,
  two ask for the same name and colour and get different ones, all ready,
  the host starts, two saboteurs are dealt; the match ends and returns to
  the lobby; start is refused while someone is not ready.
- **Secret roles reach only their owners** (`tests/hidden.rs`): every
  datagram the host sends is captured, decrypted with keys rebuilt from the
  seeds and decoded; each player's `Role` is its own, the saboteur role's
  name and the whispers appear in no crew member's plaintext, and the
  clients' worlds have no `MatchRoles` value.
- **A meeting in order under loss** (`tests/meeting.rs`): 100 ms latency,
  jitter, 5 % loss and reordering; every client receives every chat line in
  the host's order and the same vote result; same seed, same delivery hash
  and world hashes.
- **The host's replay** (`tests/meeting.rs`): a fresh host app fed the match
  log (also through `to_bytes`/`from_bytes`) has the live host's world hash
  at every tick, messages, lobby changes, a drop and a rejoin included.
- **Hostile clients** (`tests/hostile.rs`): a client with real keys sends a
  spoofed sender, messages before joining, a second join, floods, oversized
  messages, unknown types, host-only kinds, random bytes; the host never
  panics, stamps the attacker's own seat on everything it accepts, bounds
  the flood, and the honest players' meeting goes on unchanged.
- **Drop and rejoin** (`tests/sessions.rs`): a client's link is cut during
  the match, its seat stays and shows disconnected, it rejoins with its
  token into the same seat with the same role; a rejoin after the grace is
  refused; the host closing ends the match for every client.
- **Real UDP** (`tests/udp.rs`): a host and two clients over `127.0.0.1`
  join, ready, start and exchange a message.
- Unit tests: wire round trips and 20 000 random messages never panic the
  decoders; names, colours and role dealing; the match log's bytes.
