# Release 1.1: the relay (`wen relay`)

Package 13 of [1.1-2d-and-online.md](1.1-2d-and-online.md) §6. Architecture:
ADR-029 and the amendment of ADR-022 in [../DECISIONS.md](../DECISIONS.md).
It builds on the transport of [1.1-net-transport.md](1.1-net-transport.md)
(read its §3 first) and changes nothing in it but one hook (§3.6).

Recommended model and effort: Opus 5.5, high (a network-facing program that
strangers can reach; one reviewer).

Status: built on 22 November 2026 on the branch `relay` (from `r1.1`). The
tests of §6 pass on Windows (`cargo test -p wish_net`: 32 unit tests, 15 in
`tests/relay.rs` over the simulator, 1 in `tests/relay_udp.rs` over
localhost UDP; `wish_cli` `tests/relay.rs` runs `wen relay` as its own
process). Not yet run on Linux. The `wen net host --relay` and `wen net join --relay`
flags are not wired: the `net` subcommands do not exist on this base (another
lane builds them). The seam is the two transports of §3.4, which an
`Endpoint` takes as it takes a socket.

## 1. Problem

A host at home sits behind a router that drops datagrams nobody asked for, so
a player over the internet cannot reach it at its address. 1.1 does not
attempt NAT traversal (ADR-029). The user's decision of 21 November 2026: the
answer is a relay **the user runs themselves** on a small server, shipped in
both archives as part of `wen`. No hosted service, account or fee.

What the relay must do:

- route datagrams between a host and its players **by room**: a player knows
  only the relay's address and the room code;
- let only the host that registered a room receive its players (nobody else
  can take a room);
- **never see plaintext**: the end-to-end encryption between a client and the
  host stays as it is, and the room code does not pass through in the clear;
- run no game logic, write nothing to disk, keep logs without payloads;
- survive hostile traffic (invariant 7 applied to the network): floods,
  forged tokens, spoofed sources and oversized packets never crash or freeze
  it, its memory stays bounded, it amplifies nothing, and honest rooms keep
  working;
- be deterministic over the simulator, like the endpoints.

## 2. Options

| Option | For | Against |
|---|---|---|
| TURN (RFC 8656) | Standard | Large (allocations, permissions, channel binding, long-term credentials), needs accounts and a shared secret per user; nothing in Rust under a permissive licence that runs over our simulator. |
| The relay terminates the protocol (decrypts and re-encrypts) | Simple routing | The relay sees everything: breaks ADR-029's end-to-end rule. |
| The relay routes by the inner packets (connection ids, client tokens) | No envelope bytes | The relay must understand the handshake and every later version of it; the host behind the router still has to open the path first, so a registration message is needed anyway. |
| **A small envelope around the unchanged inner datagrams**, routed by a room locator and relay-assigned slots | The inner protocol, its handshake and its keys are untouched; the relay is a few hundred lines that never hold a key | 4 to 8 bytes per datagram; the relay sees who talks to whom and how much (as any router does). |

## 3. Decision

The relay is the module `wish_net::relay` (the server, the envelope and the
two transports); `wen relay` is a loop around it in `wish_cli`. No new
dependency.

### 3.1 The room locator

A room at the relay is named by a **locator**:
`SHA-256("wish-net/1 relay room" | room code)[..16]`. A client and the host
compute it from the room code; the relay never receives the code itself.

What this does and does not hide, said plainly: a room code is short (30
bits by default), so a relay **operator** who wants to can find the code from
a locator by trying every code. That is no loss against the relay: an
operator who turns active can already stand between a client and a host that
it has not pinned (the limit of [1.1-net-transport.md](1.1-net-transport.md)
§3.7, unchanged), and the room code is only the door's password, never a key:
the traffic keys come from the X25519 agreement, so **knowing the code does
not let the relay read a match**. Against a listener on the network the
locator hides the code as well as the sealed `Connect` does (no worse: the
listener sees the same locator a relay does). A pinned host key (from
discovery, or given by hand) closes the active case, as it does without a
relay.

### 3.2 The envelope

Every relay datagram starts with `W R`, the relay protocol version (1) and a
kind; numbers are little-endian. The inner datagrams are the transport's own
(`W N` ...), unchanged and sealed end to end. A relay datagram is at most
**1232 bytes** (`MAX_RELAY_DATAGRAM`: the largest UDP payload that fits the
IPv6 minimum MTU), an inner one at most 1200 (`wire::MAX_PACKET`).

| Kind | Direction | Body | Size |
|---|---|---|---|
| `Register` | host → relay | locator, host token (16 random bytes the host chose), cookie (zero the first time), padding | 96 |
| `RegisterChallenge` | relay → host | locator, cookie | 36 |
| `Registered` | relay → host | locator | 20 |
| `Unregister` | host → relay | locator, token, padding | 96 |
| `Attach` | client → relay | locator, cookie (zero the first time), padding | 64 |
| `AttachChallenge` | relay → client | locator, cookie | 36 |
| `Attached` | relay → client | locator | 20 |
| `Refused` | relay → either | locator, reason | 21 |
| `NotAttached` | relay → either | nothing | 4 |
| `HostSend` | host → relay | slot (4 bytes), inner datagram | 8 + inner |
| `ToHost` | relay → host | slot, inner datagram | 8 + inner |
| `ClientSend` | client → relay | inner datagram | 4 + inner |
| `ToClient` | relay → client | inner datagram | 4 + inner |

Reasons of `Refused`: the room is taken (another token holds it), the relay
is full (rooms or clients), the room is full, there is no such room.

### 3.3 Registering and attaching

- **A host registers** with `Register(locator, token, 0)`. The relay answers
  `RegisterChallenge` with a cookie,
  `SHA-256("wish-net/1 relay cookie" | secret | time bucket | address | locator | role)[..16]`,
  valid in its five-second bucket and the next. The host repeats `Register`
  with the cookie; only then does the relay make the room, keyed by the
  locator and bound to the host's address and token. Before that the relay
  keeps nothing (as the transport's own handshake), so a spoofed source can
  make no room. Every answer is smaller than what it answers: the relay
  cannot be used to amplify.
- **Nobody else can take the room.** A `Register` for an existing locator with
  another token is refused (`room_taken`). The same token from the same
  address refreshes the room; the same token from a new address (the host's
  router changed its port) moves the room there, after a cookie for the new
  address. A host registers again every two seconds; a room whose host has
  sent nothing for `room_idle_ms` (15 s) expires, and so do its clients. A
  host address holds one room. `Unregister` with the token closes the room at
  once.
- **A client attaches** with `Attach(locator, 0)`, receives an
  `AttachChallenge`, repeats with the cookie and gets a **slot**: a number in
  the room (from 1, never reused within the room) bound to the client's
  address. From then on its `ClientSend`s go to the host as `ToHost(slot,
  inner)`, and the host's `HostSend(slot, inner)`s go to that address as
  `ToClient(inner)`. A client silent for `client_idle_ms` (15 s, more than
  the endpoint's 10 s timeout) loses its slot. A client address holds one
  slot; attaching elsewhere moves it.
- A datagram from an address the relay does not know is answered with a
  4-byte `NotAttached` (so a host or client re-registers or re-attaches after
  the relay restarted), within the shared handshake budget.

The relay checks only that an inner datagram starts with `W N`, so it never
carries arbitrary bytes; it never opens one.

### 3.4 The transports

Two wrappers in `wish_net::relay` implement `Transport` around any transport
(a `UdpTransport` or a `SimTransport`), so an `Endpoint` runs over a relay
unchanged, with the same handshake, keys and limits:

- `RelayHost::new(inner, relay_addr, &room_code, &mut entropy)`: registers the
  room (the token comes from the entropy) and keeps it registered. Each
  client slot appears to the endpoint as its own address, a **virtual**
  address `[fd57:4e52:656c:6179::<slot>]:1` (a unique local IPv6 prefix that
  is never routed); a send to a virtual address goes through the relay.
  Datagrams that do not come from the relay pass through untouched, so one
  host takes players on the local network directly and over the internet
  through the relay on the same socket. A direct datagram whose source claims
  a virtual address is dropped.
- `RelayClient::new(inner, relay_addr, &room_code)`: the endpoint connects to
  the relay's address (`Endpoint::connect(RelayClient::new(...), relay_addr,
  ...)`); the wrapper attaches, holds the first few datagrams (at most 8) until
  it is attached, then wraps every send.

Both report `relay_state()` (`Waiting`, `Ready`, `Refused(reason)`) and turn
a refusal into a diagnostic (§5), so `wen net` and the editor can say why a
join through a relay does not start. Both retry: a refused or unanswered
registration is sent again every second, an attach every quarter second, so
a client that arrives before its host gets in when the host does.

### 3.5 Limits

| Limit | Default | Beyond it |
|---|---|---|
| Relay datagram size | 1232 bytes; inner 1200 | dropped, counted |
| Datagrams read per `update` | 4096 | the rest wait (no freeze) |
| Rooms | 256 (`--max-rooms`, at most 65 536) | `Refused(relay_full)` |
| Clients in a room | 32 (`--max-peers`, at most 256) | `Refused(room_full)` |
| Clients in all | 4096 (`--max-clients`) | `Refused(relay_full)` |
| Handshake datagrams per second (all challenges, refusals, `NotAttached`) | 512 | not answered, counted |
| Datagrams per second from one client | 1500 | dropped, counted |
| Bytes per second from one client | 1 MiB | dropped, counted |
| Datagrams per second through one room (host and clients) | 8000 | dropped, counted |
| Bytes per second through one room | 8 MiB | dropped, counted |
| Events waiting to be logged | 1024 | the oldest are dropped, counted |

Every table is a `BTreeMap` bounded by the caps above; addresses the relay
does not know get no state at all (no per-address table an attacker could
fill with spoofed sources). A client's datagrams are charged to the client
first and then to the room, so one client cannot spend its room's budget.

### 3.6 Time, determinism and the one change to the transport

The relay reads no clock: `Relay::update(now_ms)`, as `Endpoint::update`.
Over the simulator it is a pure function of the seed. The wrappers need time
to resend their registration and attach, so the `Transport` trait gains one
default method, `tick(now_ms)`, which `Endpoint::update` calls first; the
plain transports ignore it. Nothing else in the transport changes.

### 3.7 Logs

`Relay::poll_event` gives `RoomOpened`, `RoomMoved`, `RoomClosed` (idle or
by its host), `ClientAttached` and `ClientLeft`, each with the room's short
tag (the first four bytes of the locator, in hex), the slot and the address.
Payloads are never logged, nor tokens, cookies or locators in full.
Refusals and drops are counted in `RelayStats`, not logged one by one (a
flood would otherwise flood the log). `wen relay` prints one line per event
(one JSON line with `--json`) and a summary of the counts every minute.

### 3.8 `wen relay`

`wen relay [--port <p>] [--bind <address>] [--max-rooms <n>] [--max-peers <n>]
[--max-clients <n>] [--seconds <n>] [--json]`. The default port is 47 620
(`RELAY_PORT`), the default address `0.0.0.0`. It runs until stopped
(`--seconds` stops it, for tests). It is a plain subcommand of `wen`, so both
archives ship it. The secret of its cookies comes from the operating system
and lives only in memory.

It is not a tool of the control plane (invariant 4): it is a program for a
server, touches no project, scene or asset and has nothing an agent or the
editor would do in a project, as `wen mcp` is not a tool either. What a
project does with a relay (host or join through one) is a parameter of the
`net` tool and of the editor's network panel (package 14), which build the
two transports of §3.4.

### 3.9 What the relay does not protect against

- It sees **metadata**: which addresses play in which room, when and how
  much. It is the user's own server.
- An operator can find a room code from its locator (§3.1) and, if it turns
  active, stand between an unpinned client and the host, as any attacker on
  the path can (transport §3.7). It never gets traffic keys.
- Someone who knows a room's code can attach and spend that room's budget up
  to the per-client limit; the host's own room code check and limits still
  apply to them.
- A listener on the host's link can read the host token and take the room
  over from another address after a cookie: it then receives sealed packets
  it cannot open (and is the active attacker above).
- No congestion control at the relay beyond its rate limits.
- A relay that restarts forgets every room: hosts and clients register and
  attach again by themselves (`NotAttached`), but the matches that ran
  through it end by timeout and the players join again (a new room gives new
  slots).
- A datagram of another relay protocol version is dropped without an answer
  (version 1 is the first; a later version adds an answer that version 1
  peers can read, as the transport's `Reject` does).

## 4. Abuse, case by case

| Attack | What happens |
|---|---|
| Flood of junk or oversized datagrams | Dropped before any state is touched; at most 4096 read per update. |
| Spoofed `Register` / `Attach` | Answered only by a challenge to the spoofed address, smaller than the request, within the handshake budget; no state. |
| `Register` with a forged token for a live room | `Refused(room_taken)`; the room, its host and its clients are untouched. |
| Data with a spoofed client or host source | Forwarded only along an existing route; the far end cannot open it (the transport drops unauthentic packets without ending the connection). |
| One address registering many rooms | One room per host address; `max_rooms` in all. |
| Many slots | `max_peers` per room, `max_clients` in all; idle slots expire. |
| Reflection | Every answer to an unverified address is no larger than the datagram it answers; data goes only to addresses that proved with a cookie that they receive there. |

## 5. Diagnostics

`net_relay_room_taken`, `net_relay_full`, `net_relay_room_full`,
`net_relay_no_room` (from a `Refused`, in `RelayHost`/`RelayClient`), and
`net_config_invalid` for a relay setting out of range. Each is in
`wish_control::docs::DIAGNOSTICS`.

## 6. Test plan

- Envelope: every kind round-trips; random bytes, truncations and extensions
  never panic; answers to unverified addresses are never larger than the
  request.
- Over `SimNetwork` (`tests/relay.rs`): a relay node between a host and three
  clients on bad links (100 ms, jitter, 5 % loss, duplication, reordering):
  every reliable message arrives in order both ways; the same seed gives the
  same delivery hash twice. A host that takes a direct client and relay
  clients at once. A room expires when its host goes quiet; a client that
  comes before its host gets in when the host registers.
- Over localhost UDP: a relay, a host and two clients in one process with
  real sockets exchange reliable and unreliable messages.
- Hostile: floods from known and unknown addresses (limits hold, the relay
  answers within its budget), forged room tokens (refused, the room keeps
  working), spoofed sources (forwarded junk is dropped by the endpoints and
  the match goes on), oversized and random datagrams (no panic), a full relay
  and a full room (refused), and honest rooms keep exchanging messages
  throughout.
- Plaintext: every datagram to and from the relay is captured; neither the
  room code nor the bytes of any message appears in them, while the messages
  do arrive, and every inner datagram the relay forwards is a sealed
  handshake or `Data` packet of the transport.
