# Release 1.1, package 14: the control plane and the editor for online play

Plan: [1.1-2d-and-online.md](1.1-2d-and-online.md) §3 and §6, package 14.
Architecture: ADR-029 in [../DECISIONS.md](../DECISIONS.md). Builds on the
transport ([1.1-net-transport.md](1.1-net-transport.md)), replication
([1.1-replication.md](1.1-replication.md)), prediction
([1.1-prediction.md](1.1-prediction.md)), the lobby
([1.1-lobby.md](1.1-lobby.md), its §3.8 "seams") and players
([1.1-players.md](1.1-players.md)). The control plane's rules are those of
[M4-control-plane.md](M4-control-plane.md) §3, §5, §6 and §14.

Recommended model and effort: Opus 5.5, high.

Status: built on 22 November 2026 on the branch `nettool` (from `r1.1`); prediction added by package 14b on `netpredict` (§12); the relay and prediction for a process that joins an outside host added by package 14c on `netreal` (§13).
What is done and what is left is in §10.

## 1. Problem

Packages 9 to 12 built online play as libraries: `wish_net` (the
transport and a deterministic network simulator), `wish_replicate` (state
per player, inputs back, prediction), `wish_lobby` (seats, messages, roles,
the host's match log). Nothing outside their own tests can use them. The
engine's rule is that a capability exists only once the control plane has
it (invariant 4) and it can be observed and tested headless from there
(invariant 8). Concretely, package 14 must let:

- **an agent** host a match in a session, add players and bots, run it over
  a simulated bad network, look at what the host and what each player sees,
  and read round trips, corrections and bandwidth, all without people and
  with the same result every time;
- **a scenario test** (`tests/*.test.json`) play a match with bots and
  assert on the host's world and on a given player's;
- **the host's match log** become a replay file that `replay run`
  verifies;
- **`wish.json`** say which components are replicated and how the lobby is
  set up, so that files stay the source of truth (replication §2 left the
  seam);
- **a person** do the same by hand: Play with N players in the editor, a
  network panel, and `wen net host|join` for real play on a local network
  (invariant 9).

## 2. Options

**One tool or several.** A family (`net_host`, `net_join`, ...) costs a
line of the agents' guide each (the guide is held under 12,000 bytes) and
six parity rows. The existing multi-action tools (`replay`, `checkpoint`,
`packages`) show the pattern. **Chosen:** one tool, `net` (the 36th), with
an `action`.

**What a networked session is.**

1. *A new kind of object with its own id space.* Every session tool would
   need a twin (`net_step`, `net_query`, ...), or would not work on it.
2. *An ordinary session whose world is the host's.* **Chosen.** `net host`
   starts a session (`s3`) like `sim_start` does; its world is the host's
   world, and the players' worlds hang off it. `sim_step` on it steps the
   whole match (host and every player together), so `until`, `watch`,
   cancellation and scenario tests work unchanged. `entity_query`,
   `entity_get`, `capture_frame` and `describe_view` take an optional
   `player` (a seat) to look at what that player's machine has instead of
   the host's. Snapshots and forks are refused on a networked session
   (`net_session_unsupported`): a match is the host, every player and the
   network in flight, and a snapshot of the host alone would not return to
   it.

**The players' scene.** A player's machine has the same project, so it
loads the same scene (the map, the camera, the interface), but the
entities the host replicates must come only from the host (otherwise each
player would see two of everything). **Chosen:** a player's world is built
from the scene like the host's, then every entity with `Replicated` is
removed before its first tick (before physics and sight prepare).
Replicated entities arrive from the host; everything else is local.

**Time.** The endpoints need a time in milliseconds; the control plane
never reads the wall clock (ADR-027 rule 2: no answer carries one, and
simulation is deterministic). **Chosen:** the time is the tick times the
tick length (`tick_ms`, 16 by default at 60 Hz) in every mode. Over the
simulator that is exactly `SimNetwork::now_ms`. Over real UDP it is a
virtual clock too: in one process (the editor's Play with N players over
localhost) datagrams arrive between ticks, and `wen net host|join`, which
plays with people, paces its calls to one tick per tick of real time, so
virtual and real time agree. Round trips are then measured in ticks of
virtual time, not wall time, and stay out of the clock rule.

**Bots.** Two kinds, named by `drive`:
- `input` (default): the bot's input comes from the calls, held like a
  player's (`bots` and `join` take an `input` the bot holds; `step` and
  `sim_step` `players` replace it for one call). This is how a test plays
  a scripted round.
- `game`: nothing is applied from outside; the bot sends what its own
  world's `ActionState` holds after its systems ran, so game code on the
  bot's machine (which knows its seat from `LocalPlayer`) drives it.

Every bot asks to be ready once it is seated (`ready: false` turns that
off).

**Discovery.** A host over the simulator or UDP answers discovery queries
(the responder of transport §3.6, on the discovery port). `join` with
`address: "discover"` sends a query on the session's network and connects
to the first host whose game and room code match when the answer arrives
(over the simulator it arrives a few ticks later, deterministically).

**Prediction.** `wish_replicate::Predictor` needs its own app and takes
over sending the inputs; wiring the predicting client's messages into it is
lobby §3.3's open end. **Chosen for this package:** players in the control
plane mirror what the host sends and run their systems on the mirror (as
the lobby's tests do); status reports `predicted: false` and no
corrections. Prediction in the tool is left for the yardstick game's
package (§10), where the measurement says what it costs. *Superseded by
package 14b (§12): every player machine in the process predicts.*

## 3. The `net` tool

`net` is `mutates: false` like the session tools (it changes no file; the
one exception, saving a replay, is `replay save`'s). Read-only `status` is
not activity (`worth_noting`); every other action of an agent is.

| Action | Takes | Does |
|---|---|---|
| `host` | `scene`, `seed`, `players` (seats expected, 1 to 16), `bots`, `drive`, `network` or `port`, `room_code`, `host_plays`, `auto_start`, `name`, `relay` (§13) | Starts a networked session: the host's world from the scene, a `HostSession` with the project's `wish.json` `net` settings, an endpoint on a simulated network (the default; `network` sets latency, jitter, loss, duplication, reordering and its seed) or on real UDP (`port`, 0 picks one). `bots` adds that many bots at once. `auto_start`: the host starts the match at the first boundary where `players` seats are taken and ready. |
| `join` | `session`, `name`, `color`, `address` or `relay` (§13), `room_code`, `input`, `ready` | Adds a player machine to the session: an endpoint to the session's own host (default), to `address` (`host:port`, UDP), or found by `address: "discover"`. |
| `bots` | `session`, `count`, `drive`, `input`, `ready` | Adds `count` bots named "Bot 1", "Bot 2", ... |
| `start` / `end` | `session`, `outcome` | The host's own lobby requests (start when everyone is ready; end with an outcome). |
| `status` | `session`, `player` | Read-only: the lobby (phase, round, outcome, room code), every seat (name, colour, ready, connected, left, bot or not, drive, round trip, bytes received and sent, bandwidth), the host's counts (`SessionStats`, `HostStats`), the network (kind, conditions, delivery hash), and with `player` that player's machine (seat, its `LocalPlayer`, entities, world hash, the mirror's counts). |
| `step` | `session`, `frames`, `until`, `max_frames`, `input`, `players` | Advances the host and every player together, tick by tick (the same as `sim_step` on the session), with per-player input by seat. |
| `leave` | `session`, `player` | That player's machine leaves (its seat is freed in the lobby, or marked left in a running match). |
| `stop` | `session` | The host closes the session for everyone (they hear it), then the session is closed (as `sim_stop`). |

Answers carry ticks, counts and hashes, never a duration or a time of day.
Round trips (`rtt_ms`) are measured on the virtual clock (§2) and are the
same in two processes over the simulator. Bandwidth is
`bytes_received × tick rate / ticks connected`, integer arithmetic over
ticks.

### 3.1 A networked tick

```
network.step()                                    (simulator only)
now = network.now_ms()  |  (tick + 1) × tick_ms   (UDP)
host:   endpoint.update(now); discovery.update(now)
        auto start?; begin_tick(world, endpoint, tick, host's actions)
        app.step(); end_tick(world, endpoint, mark); endpoint.update(now)
        hashes.push(app.hash())
player: endpoint.update(now); begin_tick(world, endpoint)
        (drive input: wish_input::apply(world, input map, held input))
        app.step(); end_tick(world, endpoint, mark, tick)
        seated: ready once; send_input(local_actions(world)); endpoint.update(now)
```

Players step in the order they joined. Over the simulator the whole match
is a pure function of the scene, the seeds and the calls.

The host's own player (seat 0, when `host_plays`) takes input 0 (`input`,
or `players` "0"); seat `k` takes the player machine seated at `k`. A seat
not named in a call keeps the input its player holds.

## 4. `wish.json`: `net`

By addition: a project without it is read as before, and its file stays
byte-identical (the key is written only when present).

```json
"net": {
  "replicate": ["Transform", "Avatar", "NetOwner"],
  "budget_bytes": 1100,
  "lobby": {
    "min_players": 4,
    "colors": 12,
    "rejoin_grace_ticks": 600,
    "roles": [{ "name": "crew" }, { "name": "saboteur", "count": 2 }]
  }
}
```

Added by package 15 (friction F14, F16): `lobby.max_players` (1 to 16, at
least `min_players`; a peer beyond it is refused as when the match is full)
and a role's `more_from` (one more player gets it from each number of
players listed: `{ "name": "saboteur", "count": 1, "more_from": [7] }`).
`project_settings` writes the whole `net` section (F22).

`replicate` names the replicated component types (replication §2,
`ReplicationConfig::components`; managed and unknown ones are refused when a
host starts, with the replication's own diagnostics). Without the key, or
without `replicate`, a host replicates `Transform` and `NetOwner`, which is
what the lobby's own examples need. `lobby` holds the `LobbyConfig` fields a
project sets (the seed, the host's name and colour come from the call). The
file is checked with located diagnostics (`invalid_project_file`, as the
rest of `wish.json`); `check` reports it.

## 5. Scenario tests with a match

A test says `"net"` at the top, and its steps run on the networked session
(`sim_step` on it):

```json
{ "format": 1, "scene": "scenes/main.scene.json", "seed": 4,
  "net": { "players": 6, "bots": 5, "auto_start": true,
           "network": { "latency_ms": 100, "jitter_ms": 20, "loss": 0.05, "seed": 9 } },
  "steps": [
    { "until": "Lobby.phase == 'Running'", "max_frames": 900 },
    { "players": { "2": { "move": [1, 0] } }, "frames": 120 },
    { "expect": "Score.points >= 1" },
    { "expect": "LocalPlayer.joined == true", "player": 3 } ] }
```

`players` in `net` is the number of seats; `bots` fill them (one fewer
than `players` when the host plays). An `expect` with `"player": k` is
evaluated on that player's world (what its machine was sent), otherwise on
the host's. When the steps pass, the run plays the host's match log into a
fresh host app and compares its hash at every tick (`replay_verified` in
the result); a difference fails the test at the first tick that differs.

## 6. Replays of a match: format 3

`replay save` on a networked session writes the host's match log (no
`record` needed: the log is kept from tick 0):

```text
{"kind":"header","format":3,"scene":…,"scene_hash":…,"seed":…,"tick_rate":60,"code":…,"assets":…,"engine":…,"executor":…,"ticks":N,"net":{"host_plays":true}}
{"kind":"match","log":"<base64 of MatchLog::to_bytes>"}
{"kind":"hashes","bits":64,"values":"<16 hex digits per tick>"}
```

`replay run` builds a host app the way `net host` does, applies the log's
record before each tick (`wish_lobby::apply`, the same function the live
host used) and compares the hash after every tick, as for formats 1 and 2.
Formats 1 and 2 are unchanged; an engine of 1.0 refuses format 3 with its
"format the engine does not read" diagnostic.

## 7. The editor

- **Play with players** (Game menu, and a number beside the toolbar's Play
  button): a number from 2 to 16; Play then calls `net host` with
  `players: N`, `bots: N − 1`, `auto_start` and the simulated network,
  instead of `sim_start`, by `human`. The game runs as before (each frame
  is one `sim_step` on the session). The person plays seat 0 (since package 14b a seat as a predicting player, §12).
- **The player switcher**: a row of buttons over the game view, "Host" and
  "Player 1" to "Player N−1"; the game view draws the chosen player's world
  (`PictureSource::Player`), what that machine was sent.
- **The network panel** (`window.network`): seats with names, ready,
  connected, round trip, bytes and bandwidth, the lobby's phase and round,
  the host's counts. It is a `net status` call when it opens and while it
  is open, at the inspector's pace.
- Every control is one control-plane call by `human`; the parity row for
  `net` names the editor test that plays with two players by hand.

## 8. The command line

- `wen play --players N` plays with N players in one window: the host and
  N−1 bots in process over the simulator; the person is the host (since package 14b a predicting player, §12). (One
  window, not one per player: the editor's switcher shows the others.)
- `wen net host [--port P] [--room CODE] [--players N]` hosts on real UDP
  headless and prints the room code and every change of the lobby;
  `wen net join <address|discover> --room CODE [--name NAME]` joins one.
  Both are a loop of `net` calls (`host`/`join`, then `step` paced at the
  tick rate, `status` when something changed) until the match closes or
  Ctrl+C. Nothing new is needed from the control plane.

## 9. Diagnostics

New: `net_session_unsupported` (a snapshot, fork or replay recording of a
networked session), `net_not_networked` (a `net` action or `player` on a
session that is not networked), `net_player_unknown` (a `player` the match
does not have), `net_join_failed` (an address that cannot be read or
reached). Reused: the transport's, replication's and the lobby's. Each is
in `wish_control::docs::DIAGNOSTICS`.

## 12. Package 14b: prediction in the control plane

Built on 22 November 2026 on the branch `netpredict` (from `r1.1`).

**Problem.** §2 left player machines mirroring the host: over 100 ms each
way a player saw its own avatar move about 15 ticks after the key. The
prediction library ([1.1-prediction.md](1.1-prediction.md)) is done and
measured, but nothing in the control plane, the editor or `wen play` used
it, and lobby §3.3 left open how a predicting client's game messages are
sent once per tick when a correction plays a tick again.

**Options.**

1. *Predict only the person's machine, mirror the bots.* Cheaper, but a
   scenario test of a bot's seat would test something no player runs.
2. *Every player machine in the process predicts.* **Chosen.** A bot is a
   player machine like any other; its seat's `expect` checks what a real
   player's machine would have.

For the person: the host's own player has no latency to hide, so
prediction is invisible when the person is the host. **Chosen:** `net
host` takes `play_as` (`host`, the default, as before; or `player`: a
headless host, and a player machine named `name`, default "You", that
joins first and takes the session's own input). The editor's Play with N
players and `wen play --players N` use `play_as: "player"` over
`wish_control::play_network()` (50 ms each way, 5 ms of jitter, no loss),
so the person plays a seat as online players will.

**Decision.**

- A player machine (`netplay::Player`) has two worlds of the same build:
  the **mirror** (the replication client and the lobby write into it; no
  system runs on it, so it stays exactly what the host sent) and the
  **prediction** (`Predictor` over an app built like the host's: the scene
  less what the host replicates, the game code, the project's actions at
  rest). Each tick: `begin_tick` on the mirror, ready once, then
  `ClientSession::predict`, which runs `Predictor::frame_with` with the
  tick's actions (`input` drive: the held or given input; `game` drive:
  what the prediction world's `ActionState` holds). The prediction's clock
  is the match's virtual clock (`tick_ms` × 1000 µs a tick).
- `Predictor::frame_with` takes a `TickHook`, called before and after
  every tick it simulates, new or played again (`again`), with the
  mapping between network ids and prediction-world entities. The lobby
  session's hook writes `Lobby` and `LocalPlayer` into the prediction
  world when they changed (and on every replayed tick), delivers the
  host's messages into the first new tick after they arrived (kept per
  tick, delivered again when a correction replays that tick), and after
  the tick collects the game's messages (`end_tick`'s per-tick count, so a
  replayed tick sends only what it did not send before) and lobby requests
  (once per tick). They are sent after the frame. The control plane's own
  hook writes the pointer (kept per tick for replays); the actions go
  through the prediction, never `ActionState`, since `ActionState` is
  player 0's.
- **What a tool sees.** `entity_query`, `entity_get`, `expect` with
  `player` and `net status` `player` read the prediction world (where that
  machine's game runs). `capture_frame`, `describe_view`, the editor's game
  view and `wen play` draw the **presented** view: the prediction world
  copied into a world of the same build, with every mirrored entity's
  `Transform` set to where `Predictor::presented()` draws it (own player
  predicted and smoothed, the others interpolated) and transforms
  propagated; made when a picture asks for it, at most once per tick.
- **Status.** Every seat of a machine in the process: `predicted: true`,
  `lead_ticks`, `corrections`, `largest_correction_mm`; every seat the host
  serves: `late_frames` (new `Host::late_frames(player)`). With `player`:
  `prediction` (predicted and confirmed ticks, lead, round trip,
  predicted entities, confirmations, exact ones, corrections, the largest,
  replayed ticks, the longest replay, rebases, jumps, held ticks, stalls,
  late reports, the smoothing offset in mm, the host's late frames and
  input slack) and `mirror_hash`. All ticks and counts: the same bytes in
  two processes over the simulator.
- The person's machine: `machine: "you"` in the seats; the session's own
  `input` (when the host does not play) drives it; `Workspace::play_seat`
  names its seat; `play_scene`, `play_voices` and the pointer of
  `play_step` use its machine. The editor's network panel labels it "You
  (player N)" and shows it in the game view until another seat or the host
  is chosen.

**Limits, stated.** `wen net join` (this process as a player of an outside
host) still mirrors and runs its systems on the mirror; making the
session's own world a prediction is the next step for real play over UDP
(*done in package 14c, §13*).
Game code that gates its movement on `LocalPlayer.host` (as the first
tests' game does) is corrected every confirmation on a player's machine:
a predicted game runs its movement everywhere. Physics in the prediction
world is measured with the yardstick game (prediction §5).

**Tests.** `wish_lobby/tests/predicted.rs`: the lobby's meeting with five
predicting players over `BAD` with everything they send lost for 20 of
every 80 frames: their predictions are corrected and ticks in which their
game sent messages are played again, yet the host receives exactly the 25
messages (three lines, a vote and a point each; the point names the
player's own avatar through the prediction's network ids), every player
hears the 18 lines once in the host's order, and the same seed gives the
same hashes, which the host's log replays.
`wish_control/tests/net_tool.rs`:
`a_player_sees_its_own_avatar_answer_at_once_over_a_bad_network` (a
scenario test over 100 ms each way, 10 ms of jitter and 5 % loss: player
1's avatar moves on the tick its input is given in its own world while
the host's has not moved, both end where the host says, the match
replays, the same answer bytes twice) and
`the_person_plays_a_predicted_seat_and_corrections_stay_rare`
(`play_as: "player"` over the same network: every seat predicts with a
lead over 6 ticks, the person's avatar answers on the tick in its world
and in `play_scene`, corrections at most 2 % of the confirmations, no
smoothing left, at most 2 late frames at the host, and two workspaces give
the same answers byte for byte). Measured there (the simulator is
deterministic, so every run gives these): the person's machine made 351
confirmations, all exact, 0 corrections; lead 15 ticks over a measured
round trip of 224 ms; 1 jump and 13 held ticks at the start; 0 late frames
at the host, frames arriving 2 ticks early. The first test's game walks
only on the host, so there player 1's own machine is corrected on every
confirmation of its walk; `bots_play_a_match_...` now checks that it ends
where the host says with nothing left to smooth. The six-player scenario
test, the match replay and the parity rows run unchanged;
`parity_ops::an_online_match_is_played_with_two_players_by_hand` finds the
person's seat ("You (player N)") and the bot's.

## 13. Package 14c: the relay, and a joined process that predicts

Built on 22 November 2026 on the branch `netreal` (from `r1.1`).

**Problem.** Release 1.1 ends with 4 to 10 people playing the yardstick
game on a local network and through a relay. Two seams were left: the relay
([1.1-relay.md](1.1-relay.md)) existed as two transports nobody built
(`RelayHost`, `RelayClient`), and a process that joins an outside host
(`wen net join`, the editor) mirrored the host and ran its systems on the
mirror (§12, "Limits"), so over the internet a person saw their own
character move a round trip after the key.

**Decisions.**

- **One parameter, `relay`, on `host`, `join` and `bots`.** On `host` it is
  the relay the host registers its room at (with the session's room code);
  on `join` and `bots` the relay a machine reaches its host through, with
  `room_code` (default: the session's). Over UDP it is `"host:port"` of a
  `wen relay`; over the simulator it is `"simulated"`: the session runs a
  `wish_net::relay::Relay` on a node of its own simulated network (made
  before the host's node, seeded from the session's seed), so agents and
  tests play relayed matches deterministically. A real address over the
  simulator, `"simulated"` over UDP, or `"simulated"` in a session that runs
  no relay is `net_config_invalid` at `/relay`. The machines `host` adds
  itself (its bots, the person's machine of `play_as: "player"`) join
  directly; `bots` with `relay` adds relayed bots.
- **The host's socket is one socket.** `Wire` gained `RelayHost` and
  `RelayClient` variants (boxed wrappers around a `Wire`), and forwards
  `Transport::tick`, which the wrappers need to register, attach and
  re-register. A relayed host's endpoint is `Endpoint::host(RelayHost(...))`:
  datagrams that do not come from the relay pass through untouched, so
  players on the local network join it directly at its port and players on
  the internet through the relay, in one match. A relayed player's endpoint
  connects to the relay's address through a `RelayClient`; the handshake,
  keys and limits are the transport's own.
- **Binding.** Over UDP a socket that talks only to this computer (a player
  whose host or relay is at a loopback address, or a host whose relay is)
  binds to `127.0.0.1`, and the host's discovery responder binds to the
  host socket's own address. A host whose relay runs on the same computer is
  therefore reachable through the relay only (said in the guide); nothing
  binds a public address in the tests, so the system firewall never asks.
- **What status shows.** Every seat the host serves has `via`: `"relay"`
  when its peer is at a slot's virtual address
  (`wish_net::relay::virtual_slot`), else `"direct"`; a machine of this
  process says the same from its own socket. `relay` at the top: the
  address, `state` (`waiting`, `ready`, `refused` with `reason`), `role`
  (`host` or `player`) and `simulated`; for the session's own simulated
  relay its rooms, clients and the datagrams it carried and refused. A
  refusal becomes a warning once each time the state changes, with the
  relay's own diagnostic (`net_relay_room_taken`, `net_relay_full`,
  `net_relay_room_full`, `net_relay_no_room`); the wrappers go on asking,
  so the match starts once the relay lets it in. Counts and states only:
  the same bytes in two processes over the simulator.
- **A joined process predicts.** The session's own machine
  (`NetMatch::own`) is now a `Player` like the machines of §12: a mirror
  world the host writes into, and a `Predictor`. Its prediction world is the
  **session's own world**: between frames the predictor holds a stand-in
  app, and `NetMatch::tick` swaps the session's app in for the frame and back
  out after it (`Predictor::swap_app`, a four-line addition to
  `wish_replicate`; the swap comes back also when the frame fails). So every
  tool that reads a session without `player` (`entity_query`, `until`,
  `watch`, `capture_frame`, `wen play`, the editor's game view) sees what the
  person's machine predicts, and `player` with its own seat names the same
  world. The machine is the person's (`machine: "you"`), `play_seat` names
  its seat, and its picture is the presented view of §12. The old
  `tick_machine` is gone.
- **The command line.** `wen net host --relay <addr>` registers the room at
  the relay too and prints the relay's state with the lobby;
  `wen net join --relay <addr> --room <code>` joins through it (the room code
  is required). The JSON lines carry every seat's `via` and the `relay`.
- **The editor.** With no game running, the network panel (Game → Network
  panel) has a *Relay* field, a *Room code* field, *Host online* and *Join*.
  The relay's address is the person's preference (`relay` in
  `editor.json`, written only by this field), never the project's. *Host
  online* is `net host` over UDP (a free port, discoverable, `auto_start`,
  the Players count, the relay when one is set): the person plays seat 0
  and the panel shows the room code and the relay's state. *Join* is
  `net join` with the room code, through the relay when one is set, else
  `address: "discover"` on the local network; the joined game is predicted
  and the panel's switcher shows "You (player N)". The seat table has a
  *Path* column (relay or direct). Every control is one `net` call by
  `human`.

**Not done.** A host's room is not unregistered when the session stops (the
relay forgets it after 15 s of silence; hosting again with the same code in
that time is `net_relay_room_taken`, and the registration goes on trying).
The editor's *Host online* uses a free port, so a player on the local
network finds it by discovery (*Join* without a relay), not by a typed
address. Neither has been tried by people on two computers yet; that is the
release's own test.
