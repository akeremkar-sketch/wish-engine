## 1. Problem

The yardstick game of release 1.1 is top-down 2D with characters that walk,
in many colours, and an interface of panels. Sprites until now were one
picture each: a `Sprite` showed `image` cut to `rect`, and game code
animated it by writing `rect` itself, frame by frame. There was no file that
says how a picture is cut and which frames make a walk, no animation the
engine plays, no way to draw a panel at any size without stretching its
border, and the overlay pass copied every picture into one atlas, texel by
texel, on every frame.

What this package must give:

- a sprite sheet file: a picture, how it is cut into frames, named clips;
- an animator the engine plays deterministically, that game code can switch;
- tint per sprite and nine-slice drawing;
- sprites drawn in batches, measured;
- the file kind everywhere a file kind must be (`check`, `fmt`, `migrate`,
  `watch`, `asset_list`, `asset_info`, `wen mv`, `asset_create`, checkpoints,
  the editor).

## 2. The sheet file

```json
{
  "clips": {
    "idle": { "fps": 2, "frames": [0, 1] },
    "walk": { "fps": 8, "frames": [4, 5, 6, 7] },
    "fall": { "fps": 6, "frames": [2, 3], "loop": false }
  },
  "format": 1,
  "grid": { "columns": 4, "frame": [32, 32], "rows": 2 },
  "image": "assets/sprites/crew.png"
}
```

- `*.sheet.json`, format 1. Top-level keys, no wrapper object: `image` (a
  PNG of the project), then **either** `grid` (`frame` [w, h], `columns`,
  `rows`, optional `margin` [x, y] and `spacing` [x, y]; frames numbered
  from 0 left to right, then down) **or** `frames` (`[[x, y, w, h], ...]`
  in the picture's pixels from its top left), and `clips` by name, each
  `frames` (sheet frame numbers in order; a number may repeat to hold a
  frame), `fps` (default 10, at most 240) and `loop` (default true).
- Options considered for its content: a schema type, as `MaterialFile` is
  for material files, or a hand-written reader. A schema type is plain data
  of fixed size (`Plain`), and a sheet is lists of any length (frames, clips,
  a clip's frames). Decision: **a reader of its own** in `wish_asset::sheet`
  (`parse_sheet`, `check_sheet`, `SheetDocument { sheet }`, `Sheet`,
  `read_sheet_file`), written to the material reader's pattern: every
  mistake a diagnostic with the file, the JSON pointer, the line and column,
  and a hint (`type_mismatch`, `unknown_key` with the closest name,
  `value_out_of_range`, `wrong_length`, `invalid_asset_ref`,
  `missing_format`, `unsupported_format`, and `sheet_invalid` for what a
  sheet must say: an image, one way of cutting, frames in clips).
- Limits: 256 KiB a file (`sheet_file_too_large`, never read whole beyond
  that, the same reader everywhere), 4096 frames, 256 clips, 1024 frames a
  clip, clip names 1 to 64 bytes, sides up to 4096 pixels. Whole numbers may
  be written `32` or `32.0` (a number box writes the latter); the editor
  writes `32`.
- Canonical form is the scene files' (`wish_scene::json::to_canonical`);
  load then save is byte-identical, defaults that are not written stay out.
- A document and an asset (like a material file): `wish_asset::is_document`
  and the asset index include it (`index::is_document_asset`); `check` reads
  every sheet (and the picture's PNG header, for
  `sheet_frames_outside_picture`, a warning); `wen fmt` rewrites it from its
  canonical text; `wen migrate` takes format 1 as current; `wen watch`
  reloads on it as on every project file; `wen mv` rewrites the picture
  reference inside it and references to it in scenes and prefabs, and a
  sheet keeps its ending (`kind_change`); checkpoints keep and restore it
  (it is one of their kinds now). A sheet cannot name another sheet.
- `asset_create` with a `.sheet.json` path and `sheet {...}` makes one, all
  or nothing, checked first (`/sheet/...` pointers in errors), canonical,
  with `dry_run` and `overwrite`; a picture that is not there yet is a
  warning and the file is still made. `asset_list` kind `sheet`;
  `asset_info` gives `sheet` (image, `image_exists`, `frame_count`, the
  first 256 frames' rectangles, clips with frames, fps and loop) and
  `written`.

## 3. Sprite animation

### 3.1 The component

`SpriteAnimator` (`wish_types::sprite`, in the SDK and its prelude):

| Field | Type | Default | Meaning |
|---|---|---|---|
| `sheet` | AssetRef | none | the `*.sheet.json` |
| `clip` | Text | empty | the clip by name; empty: no clip, `frame` is the sheet's own frame number (a still) |
| `playing` | bool | true | whether time moves; a clip that does not loop sets it false at its end |
| `speed` | f32, -10 to 10 | 1 | 2 twice as fast, -1 backwards |
| `time` | f32, s | 0 | seconds into the clip; written by the engine, write it to jump |
| `frame` | u32 | 0 | with a clip: its place in the clip's frames, written by the engine; without: the sheet's frame |

`SpriteAnimator::play(clip)` (plain Rust on the type, so game code has it):
another clip starts at its beginning (time and frame 0), the same clip runs
on; either way it plays. Calling it every tick is how game code says "walk
while moving, idle while not".

Why a component of its own and not fields on `Sprite`: a still sprite (most
of a map) carries nothing it does not use, and the inspector's `Sprite` box
stays short (the lesson of the material package, M12-materials §3.1).

### 3.2 Where the frame is decided

Options:

1. The animation system writes the frame's rectangle and the sheet's picture
   into `Sprite.rect` and `Sprite.image`; the renderer stays as it was.
2. The world holds the clip, the time and the frame's place in the clip; the
   renderer is given the sheets (as it is given material files) and turns
   that place into a rectangle of the sheet's picture.

Decision: **2**. With 1, a scene that is not running (the editor's view, a
`capture_frame` of a scene file) would show the sprite's own `image`/`rect`,
a white square, until a tick ran; and `Sprite.rect` would be a field the
engine overwrites behind the person who typed it. With 2 the frame shown is
the clip's first at tick 0 by construction, and `describe_view` can say
clip, frame and sheet frame for a scene as for a session.

What decides the future is in the world, so snapshots, forks and replays
hold it exactly; which rectangle that means is a drawing question.

### 3.3 The system

Part of the existing `animation` system (`wish_anim::step` now runs model
clip players, then sprite animators: one reserved name, already ordered
after every game system and before transform propagation and render
extraction). For each animator with a clip, in entity order: `time +=
Time.delta × speed` while playing; a looping clip wraps (`rem_euclid` of its
length, frames / fps); a clip that does not loop clamps to its ends, stops
(`playing = false`) and sends `AnimationFinished { entity }` once (the event
models already send); `frame = floor(time × fps)`, modulo the frame count or
clamped. Time comes from the tick (`Time.delta`), never the clock; numbers
game code may have broken (not finite, speed out of range) are cleaned
before use. An animator without a clip, or whose sheet or clip is not known,
is left as it is.

What the system needs of the sheets (frame count, fps, loop per clip) is an
extension (`wish_anim::SpriteClips`, ADR-026), which the control plane fills
when a session starts from the project's sheets (`Workspace::sprite_clips`,
cached by length and modification time, read with the size cap; a sheet with
a mistake has no clips there). Every way a world runs is a session (tools,
`wen play`, the editor's play, exports), so this is the one place. As with
model clips, a sheet saved during a session is used from the next session.

**Replays:** sheets are read by the simulation (they decide `frame`), so they
are in the replay header's `assets` fingerprint (written only when a project
has sheets, so every existing fingerprint is unchanged). A test changes a
clip's fps between recording and playing: the replay diverges and says
`replay_assets_changed`.

### 3.4 In the renderer and the tools

- Extraction reads the animator into `SpriteView.animation` (sheet, clip,
  frame). `Renderer::set_sprite_sheet` / `remove_sprite_sheet` /
  `sprite_sheet` keep sheets as `SpriteSheet { image, frames, clips }`; the
  renderer never reads a file.
- The control plane loads the sheets a scene's animators name before its
  pictures (`render::load_sprite_sheets`, called from `load_ui_pictures`,
  which every picture already goes through: the tools, the editor,
  `wen capture`/`view`/`play`), then the sheets' pictures with the rest.
  A sheet that cannot be used is `sheet_not_loaded` (the sprite shows its
  own picture); a clip it lacks is `sprite_clip_not_found` (its first frame
  shows), a still frame beyond it `sprite_frame_not_found` (its last shows).
- `describe_view` lists, for a sprite that shows a sheet, `clip`, `frame`
  (its place in the clip) and `sheet_frame`; `entity_get` shows the
  animator as any component.
- `check` warns `sprite_clip_not_found` where a scene or prefab writes a
  clip its sheet lacks (with the sheet's clips in the hint), and
  `SpriteAnimator.sheet` naming a file that is not a sheet is
  `not_a_sheet_file`.

## 4. Tint and nine slices

**Tint:** `Sprite.color` already multiplied the picture (linear RGB and
alpha), as Unity's `SpriteRenderer.color` and Godot's `modulate` do. Its
documentation now calls it the tint and says what it is for (one white or
grey character, many player colours). No new field: a second colour that
also multiplies would be two ways to say one thing. A tint that keeps some
parts of a picture (a visor) is a second picture layered on top, or a later
"tint mask" if the yardstick game shows it is needed.

**Nine slices,** options: fields on `Sprite`, or a new component. Decision:
**two fields on `Sprite`**, `size` ([w, h] picture pixels; 0 keeps the
picture's size) and `slice` (borders [left, top, right, bottom] in picture
pixels; all 0: not sliced). A sliced sprite is still one picture standing in
the world with an anchor, a layer, flips and a tint, so it is a `Sprite`; a
second component would have to repeat all of that or depend on the first.
`size` is useful alone too (a sprite drawn at a size other than its pixels
without scaling the entity, so children are not scaled). Both are
additions with defaults that leave every existing sprite as it was; the
recorded defaults of format 2 gained them (§7).

Drawing: the corners keep their size (borders divided by
`pixels_per_unit`), the edges stretch along their length, the middle both
ways; drawn smaller than its borders, the borders shrink in proportion
(nothing turns inside out); flips mirror where each piece goes as well as
its picture. A sliced sprite is up to nine rectangles of the same batch.

For the interface: the in-game interface's `UiImage` does not slice yet. A
panel of the yardstick game can be a sliced sprite under a camera; slicing
`UiImage` is the same cutting in screen pixels and is noted for the package
of the interface work (package 12, lobby and meetings).

## 5. Batches

Before: every frame, the overlay built one atlas on the CPU (4096 texels
wide, every picture of the frame copied into it texel by texel), uploaded it
whole, and wrote six vertices (240 bytes) per rectangle; consecutive
rectangles with the same sampling were one draw.

Now (`crates/wish_render/src/sprites.rs`, shader `sprite_pass.wgsl`):

- **Pictures are kept on the GPU.** Each picture is uploaded once, as a
  texture of its own (one level, sRGB, through the counted
  `Gpu::create_texture`), the first time a frame draws it, and kept until
  the picture changes (`set_ui_picture` forgets its copy). Plain colour and
  particles sample a white texel made once.
- **One instance per rectangle,** 84 bytes: the four corners (still worked
  out on the CPU, so every sprite lands on exactly the pixels it did), the
  picture's part, the colour, the disc flag. The shader's `vs_instance`
  picks the corner of each of the six vertices.
- **A batch** is a run of consecutive rectangles, in drawing order, with the
  same picture and the same sampler: one instanced draw. The order is the
  old one (layer, then farther first, stable), so batching never changes
  what is in front.
- GPU rules kept: the frame's bind groups are its own (one over the uniform
  buffer, one per picture and sampler, over textures and samplers only), the
  uniform and instance buffers come from the pool and are filled through the
  queue, everything inside `Gpu::checked`; `vs_instance` is in
  `ENTRY_POINTS` (a shader override folder with the old `vs_main` gets
  `shader_entry_point_missing` instead of a GPU error).
- The sprite test's golden image (`sprites.png`) is byte-identical after the
  change (checked byte by byte, not only within the tolerance).

### 5.1 Measurement

`cargo test --release -p wish_render --test sprites measure -- --ignored
--nocapture` (`WISH_BENCH_HARDWARE=1` for the hardware adapter): 5,000
sprites of one 256 × 256 sheet in a 100 × 50 grid, each about 11 pixels
square, every frame showing each sprite's next 32 × 32 frame (animated),
sharp sampling, 1280 × 720, drawn and read back; 3 frames to warm up, the
median of 20. Before is `r1.1` (`a389ae3`) with the same test file. Windows
10 19045, release, the machine otherwise idle at below-normal priority on
four cores.

| Adapter | | Before | After |
|---|---|---|---|
| Software (Microsoft Basic Render Driver) | 5,000 animated sprites | **346.8 ms** (3 runs: 352.5, 346.8, 344.3) | **145.3 ms** (2 runs: 146.5, 145.3) |
| | the same sprites, too small to cover a pixel | 278.0 ms | 72.9 ms |
| | the picture without the sprites | 23.5 ms | 23.2 ms |
| Hardware (NVIDIA GeForce RTX 3060 Ti) | 5,000 animated sprites | 5.1 ms | **3.5 ms** |
| | too small to cover a pixel | 5.5 ms | 4.2 ms |
| | without the sprites | 1.7 ms | 1.8 ms |

Draw calls were 3 in both (sky, tone mapping, one sprite draw): the old
code already drew one run per sampler; what changed is the work per frame.

- On the software adapter the sprites went from about 323 ms to about
  122 ms (2.6 times less). Most of what is left is the software rasterizer
  itself: preparing the frame's 5,000 instances on the CPU takes about
  1.6 ms (measured with a probe that is not kept), about 50 ms is vertex and
  triangle work that remains even when no pixel is covered, about 70 ms is
  filling and blending the pixels.
- On hardware a frame with 5,000 animated sprites costs 1.7 ms more than an
  empty one, against 3.4 ms before; most of the frame is the readback.
- Trigger to measure again: the yardstick map's sprite count with tiles
  (package 5), or a frame budget miss on the software adapter in CI.

## 6. The editor (parity)

- *Assets > New... > Sprite sheet* makes a sheet of the selected picture
  (or the project's first): one frame the picture's size
  (`asset_create`, by `human`).
- A selected sheet shows its fields where the browser shows the file, with
  the inspector's widgets over a schema the browser makes from the file:
  `image`; `grid` (`frame`, `columns`, `rows`, `margin`, `spacing`) or
  `frames` (JSON); each clip's `frames` (JSON), `fps`, `loop`. A clip is
  added (a name and *Add clip*) and removed (*Remove*); *Switch to
  rectangles* / *Switch to a grid* cuts the picture the other way with the
  frames it has. Every change is one `asset_create` over the file by the
  person, applied to what the file writes now (read again first: a clip an
  agent changed meanwhile is kept; a sheet that does not read is not
  overwritten).
- A `SpriteAnimator` is added and set in the inspector like any component;
  `size` and `slice` are `Sprite` fields there.
- `wish_editor::parity::PARITY`: the `asset_create` row names the sheet and
  its test, `parity_ops::a_sprite_sheet_is_made_and_changed_by_hand`.
- A fix found on the way: a press on a menu item that reaches over the
  scene view (the *New...* menu, one item taller now) was also taken as a
  click on the view and selected the entity behind it. A press while a
  popup is open, or on a foreground layer, is no longer a pick
  (`app.rs`, `view_input`); the material file test now also asserts that
  nothing was selected.
- New interface text, translated in all 11 languages: *Sprite sheet*, *Add
  clip*, *new clip name*, *Switch to rectangles*, *Switch to a grid*, *Rectangles: ...*.

## 7. What it changes in the world's types

- `Sprite` gains `size` and `slice` (defaults 0, left out of files), so its
  layout and the registry fingerprint change; `SpriteAnimator` is a new
  engine component (registered by `wish_anim::register`). World hashes of
  worlds with the engine's types move, as with every package that added a
  type (M12-render-foundation §6); no recorded hash in the repository covers
  these types (the recorded values in `wish_core`, `wish_ecs` and
  `wish_physics` register other types).
- `crates/wish_scene/src/defaults/format-2.json` gained `Sprite.size`,
  `Sprite.slice` and `SpriteAnimator` (`UPDATE_DEFAULTS=1 cargo test -p
  wish_control --test look_lock`); `format-1.json` is unchanged.
- Game code compiled against an older SDK must be rebuilt (`wen sdk`, then
  `script_build`): `Sprite`'s layout changed.

## 9. Not in this package

- Per-frame durations and pivots, events on frames, blending between clips:
  the yardstick game does not need them yet.
- A tint mask; slicing `UiImage` (§4).
- Sheets saved during a session are used from the next session (as model
  clips); the editor's views pick a changed sheet up at the next picture.
- A checkpoint's picture uses the project's sheets as they are now (it keeps
  the sheet files and restores them, but its preview does not read them from
  the checkpoint, as it does material files).
- Tilemaps (package 5) will reuse sheets for tilesets where they fit.
