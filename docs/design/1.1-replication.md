# Release 1.1, package 10: replication with per-player visibility

Plan: [1.1-2d-and-online.md](1.1-2d-and-online.md) §3 and §6, package 10.
Architecture: ADR-029 in [../DECISIONS.md](../DECISIONS.md). Builds on the
transport ([1.1-net-transport.md](1.1-net-transport.md)) and on players
([1.1-players.md](1.1-players.md)).

Recommended model and effort: Opus 5.5, xhigh (a foundation package of the
networking area).

Status: built on 21 November 2026 on the branch `replication` (from `r1.1`).
The crate is `wish_replicate`; its tests are listed in §8 and pass
(`cargo test -p wish_replicate`).

## 1. Problem

The host runs the one true simulation (ADR-029). Every other machine must
receive, every tick, the part of the host's world that its player may see,
and nothing else: in a hidden-role game a single byte of the wrong entity
tells a player who the saboteur is. Concretely:

- **What is sent.** Components of entities marked as replicated, chosen by
  a rule per entity: everyone, its owner only, a group (ghosts), players
  within a distance, players within sight (a later package), or a set of
  players decided by game code.
- **Cheaply.** A delta of what changed against what that player is known to
  have, encoded by the schema (the engine knows every field), within a byte
  budget per player per tick, with a deterministic order when over it.
- **Robustly.** Datagrams are lost, duplicated and reordered; a player can
  join a running match; a client may be modified or hostile and must not be
  able to crash, freeze or confuse the host.
- **Deterministically.** Over the network simulator, the same seed gives the
  same client worlds byte for byte (the basis of network scenario tests).
- **Inputs back.** Clients send their actions stamped with ticks; the host
  writes them into `PlayerActionState` (players package).

Out of scope, with seams left for them: prediction, reconciliation,
interpolation and tick sync (package 11), messages and the lobby (12),
`wen relay` (13), the `net` tool, the editor's Play with N players and the
project setting that lists replicated types (14), line of sight (7).

## 2. Options

**Network model.** Fixed by ADR-029: host-authoritative, per-player
visibility, deltas against acknowledged state.

**What a delta is made against.**

1. *Whole-snapshot baselines* (Quake 3): the host keeps the state it sent
   per tick; the client acknowledges the newest it applied; the next message
   is a delta against that whole state. Simple and exact while every message
   carries every difference. **Rejected after it was built and measured:**
   with a byte budget a message cannot carry every difference, and a message
   built on an older baseline silently takes back what a newer message
   carried (an entity updated at tick 10 but deferred at tick 11 jumps back
   when tick 11, built on the baseline of tick 8, is applied). Under budget
   pressure the client's copies flickered backwards and the priority order
   showed no effect (measured ratio 1.4 where 4 was asked).
2. *Per-entity acknowledged state* (the scheme of Tribes and Unreal's
   property replication, kept per entity rather than per property):
   **chosen.** The host remembers, per player and per entity, the newest
   state the client acknowledged and whether a message carrying the entity
   is still unacknowledged. Each section names the tick of the base it
   changes. The client keeps a few states per entity by tick and shows, per
   entity, the newest one. A budget only delays an entity; it never takes
   anything back, and the priority order works as asked (measured ratio 2.5
   to 6 for a ratio of 4, see §8).

**Which components of a replicated entity are sent.**

1. *All of them by default, with an opt-out.* Less to write; but a secret put
   on an entity everyone sees (a `Role` on the avatar) leaks silently, and a
   leak is exactly what the genre cannot afford. Engine-derived components
   (`GlobalTransform`) would also be sent for nothing.
2. *A list of types* (Unreal's replicated properties, Bevy replicon's
   `replicate::<T>()`). Forgetting a type is loud (the client visibly misses
   it, and the tests see it); forgetting an opt-out is silent. **Chosen:** the
   host's `ReplicationConfig::components` names the replicated component
   types. The list is configuration of the host, not data in the world: the
   `net` tool of package 14 reads it from the project (`wish.json`), so files
   stay the source of truth. Managed components (`Hierarchy`) are refused.

**Entity ids on the wire.** Sending the host's entity ids leaks how many
entities exist (gaps in the numbers) and lets a client name entities it never
saw. **Chosen:** per-player network ids, given in the order entities first
become visible to that player, never reused, kept while the host entity
lives or the client may hold it. A client can only ever name what it has
seen; the host resolves an id through that player's own table
(`Host::resolve`), and only while the player may see the entity, so a forged
or stale id resolves to nothing.

**Names.** Engine types that games are likely to name themselves get a
prefix (as `BodyVelocity` did in M6): `NetOwner`, `NetViewer`, `NetGroups`,
`NetVisibility`. `Replicated` keeps its plain name.

## 3. Decision

### 3.1 World types (`wish_types::net`, registered by `wish_replicate::register`)

| Type | Kind | Meaning |
|---|---|---|
| `Replicated { visibility, groups, players, radius, priority }` | component | The entity is replicated, to whom, and how urgently. |
| `NetVisibility` | enum | `Everyone`, `Owner`, `Group`, `Near`, `Sight`, `Players`. |
| `NetOwner { player }` | component | The player who owns the entity. The owner always sees what it owns, whatever the rule. |
| `NetViewer { player }` | component | A point a player sees from (an avatar, a camera), for `Near` and `Sight`. |
| `NetGroups { players: [u32; 16] }` | resource | Each player's group bits (bit 0 = ghosts, say); game code changes them. |

All four are in the SDK's prelude, so game code reads and writes them.

Rules, for player `p` and a replicated entity `e` (the owner always sees it):

- `Everyone`: every player.
- `Owner`: only the owner.
- `Group`: players whose `NetGroups` bits share a bit with `e.groups`.
- `Near`: players with a `NetViewer` within `radius` metres of `e`. Positions
  are `GlobalTransform`'s translation, else `Transform`'s; an entity without
  either is never near.
- `Sight`: `Near` for now. The line-of-sight package (7) narrows it to "and
  not behind a wall" through a component its vision system writes; it can
  only ever remove players, never add them.
- `Players`: the players whose bit is set in `e.players`. **This is the
  filter decided by game code:** a system computes any rule it likes and
  writes the bits; the replicator never calls into game code.

An entity that leaves a player's view (hidden or despawned: the client
cannot tell which) is removed from that client's world. An entity
reference to an entity the player may not see is sent as "none".

`priority` (0.01 to 1000, default 1) weighs the entity when the budget is
short (§3.5). A value that is not a number counts as the default; radius
values below 0 or not numbers count as 0.

### 3.2 The crate `wish_replicate`

It depends on `wish_core`, `wish_ecs`, `wish_schema`, `wish_net` and
`wish_types` (plain declarations: the players' and the net types, and
`Transform`/`GlobalTransform` for positions) and on nothing else of the
engine. Parts:

- `layout`: from a component's schema, its **leaves**: plain byte ranges, text
  handles and entity references. Primitive fields are leaves; a type with more
  than 64 of them uses its merged field spans instead (fewer, larger
  leaves). Padding is never part of a leaf; values are read with
  `World::component_bytes`, which copies field spans only.
- `value`: the canonical, world-independent form of a component: its bytes
  with padding, text slots and entity slots zeroed, its strings, and its
  entity references as the receiving player's network ids (0 = none).
- `wire`: the message formats (§4), as pure encode/decode functions with
  limits; the decoder never panics on any input.
- `visibility`: the rules of §3.1, read once per tick for all players.
- `host`: `Host` (per player: network ids, what the client is known to have
  of each entity, what each unacknowledged message carried, accumulated
  priorities, buffered inputs).
- `client`: `Client` (types from the welcome, a few states per entity by
  tick, the mapping from network ids to its own entities, its inputs).
- `input`: writing players' input frames into `PlayerActionState`, with the
  same cleaning and edges as `wish_input::apply_players` (a test checks they
  agree byte for byte).

Neither side owns the transport: `Host::handle_event` and
`Client::handle_event` take `wish_net` events and say whether they used them
(so the lobby of package 12 can share the channel), and `send` takes the
`Endpoint`. Message kinds from 0 to 63 are replication's; any other kind is
passed back to the caller.

### 3.3 A host tick

1. `endpoint.update(now)`, then `host.pump(world, endpoint)` (or
   `handle_event` per event): `Connected` gives the peer a player id (the
   lowest free from 1; 0 is the host's own player) and raises
   `Players.count`; `Disconnected` frees it; `Message` reads an input.
2. The host's own input (`wish_input::apply`, player 0).
3. `host.apply_inputs(world, tick)`: for each player, the newest frame stamped
   at or before `tick` (held when none is newer), written into
   `PlayerActionState` (entry 0 copies `ActionState`).
4. The game's systems.
5. `host.send(world, tick, endpoint)`: per player, the visible set, the
   target state, and a message carrying every entity whose target differs
   from what the client acknowledged, or that a message still unacknowledged
   carried, within the budget.

**Joining a running match.** A joining player gets a `Welcome` (its player
id, the tick, the replicated types with their schema fingerprints) and then
**a full snapshot of what it may see, on the reliable channel**, every state
whole, up to `join_bytes`. The host counts the snapshot as acknowledged at
once (the reliable channel will deliver it); unreliable messages sent before
it arrives name it as their base, and the client reads them once it has. A
world bigger than `join_bytes` is cut by priority like any tick, and the
rest follows in later messages.

### 3.4 A client tick

1. `endpoint.update(now)`, then `client.pump(world, endpoint)`: every section
   of a state message becomes a state of its entity at that tick (its base
   state plus its operations); a message whose every section had its base is
   **read whole** and acknowledged. Per entity, the world shows the newest
   state: spawns, despawns, component writes and removals go through
   `insert_bytes`/`remove_by_id`, which validate values and refuse managed
   components. Texts are interned in the client's world; entity references
   are mapped to the client's entities (resolved again when the entity they
   name appears).
2. `client.send_input(endpoint, actions)`: the frame is stamped
   (`client.stamp()` = the newest host tick seen plus `input_lead`) and sent
   with up to seven earlier frames the host has not confirmed, and the
   acknowledgements: the newest message read whole and a 64-bit mask of the
   ones before it. A predicting client stamps each frame with its own
   predicted tick instead (`queue_frame` + `send_queued`, driven by
   `Predictor::frame`; [1.1-prediction.md](1.1-prediction.md)).

If 32 messages in a row cannot be read whole (a base is gone), the client
asks for a resync: the host answers with a new reliable snapshot, at most
once every 64 ticks.

### 3.5 Budget and priority

Per player per tick the state message is at most `budget_bytes` (default
**1024 bytes**: one fragment, so one datagram, so a lost datagram loses one
tick only). Removals come first (a few bytes each). Then the entities to
carry in order of **accumulated priority** (each tick an entity waits it
gains its `priority`, in thousandths, as an integer), ties by network id; an
entity whose section does not fit is skipped and smaller ones after it may
still go; the first section of a message may exceed the budget (up to the
largest message), so one large entity is never starved. An entity that is
carried starts again from zero, and is carried again (as redundancy against
loss) until a message carrying it is acknowledged. Everything here is
integer arithmetic on ordered maps: the same world gives the same bytes.

### 3.6 Limits (a hostile client)

| Limit | Value | Beyond it |
|---|---|---|
| A client's message | 2 KiB | dropped, `net_message_invalid` |
| Frames per input message | 8 | dropped, `net_message_invalid` |
| Actions per frame | 32 | dropped, `net_message_invalid` |
| A frame stamped ahead of the host | `input_window` (120 ticks) | frame dropped, `net_input_out_of_window` |
| A player id that is not the peer's | — | message dropped, `net_input_wrong_player` |
| An acknowledgement of a tick never sent | — | ignored, `net_ack_invalid` |
| A resync request | one per 64 ticks | ignored |
| Buffered input frames per player | `max(history, input_window)` | the oldest are dropped |
| Diagnostics kept | 256 | the oldest are dropped and counted |
| Players | 15 peers (ids 1 to 15) | the peer is disconnected, `net_players_full` |
| Unacknowledged messages remembered per player | `history` (64) | the oldest is forgotten (its entities are carried again) |
| States kept per entity on a client | `history` (64) | the oldest are dropped |

Every check happens before anything is stored; nothing a client sends can
make the host allocate beyond these bounds, and no message is ever
`unwrap`ped. A client message never names a host entity; later message kinds
that name entities resolve them through `Host::resolve(player, net_id)`.

## 4. Wire format

All integers little-endian; `varint` is unsigned LEB128 of at most ten bytes
(an overflowing one is malformed). Every message starts with a kind byte.

**Host to client.**

`Welcome` (kind 1, reliable):

```
u8 version (2; 1 before the prediction package added the state flags)
varint player
varint tick
varint type count (at most 256)
per type: u8 name length (1 to 128), name (UTF-8), 16-byte schema fingerprint
```

`State` (kind 2; unreliable every tick, reliable for a join or resync snapshot):

```
varint tick
varint input ack + 1       (0: none; the newest input frame of this player applied)
u8 flags                   (bit 0: complete, nothing left out by the budget;
                            other bits 0; added by the prediction package)
varint removed count, then each removed network id (ascending)
varint entity count, then per entity, ascending by network id:
  varint network id (at least 1)
  varint base gap          (0: from nothing; else the base is tick - gap)
  varint op count, then per op, ascending by type index:
    varint (type index << 2 | op)    op: 0 remove, 1 whole value, 2 changed leaves
    whole value:    every leaf
    changed leaves: ceil(leaves / 8) mask bytes, then each leaf whose bit is set
leaf: plain = its bytes; text = varint length (at most 64 KiB) + UTF-8;
      entity reference = varint network id (0: none)
```

A section from nothing carries whole values only.

**Client to host.**

`Input` (kind 16, unreliable):

```
varint player              (must be the peer's own)
varint newest message read whole + 1 (0: none)
u64 mask                   (bit i: the message of tick newest - 1 - i was read whole)
u8 flags                   (bit 0: resync request)
u8 frame count (0 to 8)
per frame, newest first: varint tick (first) or gap to the previous (at least 1),
  u8 action count (at most 32), per action: u32 action id, f32 x, f32 y
```

Actions at rest are not sent. Unknown action ids are ignored; values are
cleaned (not a number: 0; clamped to -1..1) exactly as `wish_input` does.

## 5. Diagnostics

`net_component_unknown`, `net_component_not_replicable` (host
configuration; `net_config_invalid` for a setting out of range),
`net_message_invalid`, `net_input_wrong_player`, `net_input_out_of_window`,
`net_ack_invalid`, `net_players_full` (host), `net_types_mismatch`,
`net_state_invalid` (client). Each is in `wish_control::docs::DIAGNOSTICS`.
A host keeps them in a bounded list (`Host::take_diagnostics`), with counts
in `HostStats`.

## 6. Observability

`HostStats` and `ClientStats`: messages and bytes, entities deferred by the
budget, sections whose base was missing, messages dropped as invalid,
resyncs. `Host::target(player)` is the state the player should have after
the last send, and `Client::mirror(world)` reads the client's world back into
the same form: tests compare the two for equality. `Host::network_ids`,
`Host::resolve`, `Client::entity` and `Client::network_id` map the ids. The
`net` tool (package 14) will put these into the control plane.

## 7. Recorded values

Registering `Replicated`, `NetOwner`, `NetViewer` and `NetGroups` with the
engine's types moves the world hash of every world that registers them (the
registry fingerprint), as every added engine type does; no recorded hash in
the repository covers such a world. Their defaults are recorded in
`crates/wish_scene/src/defaults/format-2.json` (`UPDATE_DEFAULTS=1 cargo test
-p wish_control --test look_lock`); `format-1.json` is untouched.

## 8. Tests

`cargo test -p wish_replicate`: one host world and up to four client worlds
stepped together over a `SimNetwork` in one process (`tests/common`). The
test game: each player has an avatar everyone sees (moved by its player's
input), a secret only its owner sees (holding a marker number and a marker
text), a treasure seen only within 3 m (player 1 walks past it), a ghost
light seen only by the ghosts' group (player 3), and a beacon everyone sees
whose entity reference points at player 2's secret.

- **Hidden information** (`tests/hidden.rs`): over 5 % loss, 100 ms latency,
  jitter and reordering, every datagram the host puts on the network is
  captured, decrypted with keys rebuilt from the test's seeds, reassembled
  and decoded: no state message to a player carries a section of an entity
  that player could not see at that tick; the other players' marker numbers
  and texts appear nowhere in its plaintext (its own do, so the search
  works); the treasure's marker only in player 1's, the ghost's only in
  player 3's; every unreliable state message is within the budget.
- **Determinism** (`tests/simulated.rs`): two runs with the same seed give
  the same client world hashes at every tick and the same delivery hash; a
  different seed gives different ones.
- **Exactness:** with no loss, and under loss, latency, jitter and
  reordering, every time a client reads its newest message whole and shows
  nothing newer, its world read back equals the host's target for that
  player at that tick (checked at every such tick, several hundred per
  client); after the inputs stop, every client converges.
- **References:** only player 2's beacon points at its secret; the others'
  point at nothing.
- **Joining a running match:** a fourth client joins at tick 120, gets its
  reliable snapshot, matches the host's target and walks.
- **Budget:** 200 entities through a 256-byte budget: the budget binds, the
  entities with priority 4 are updated 2.5 to 6 times as often as those with
  1, none is starved, and the world converges once still.
- **Hostile clients** (`tests/hostile.rs`): a client with real keys sends,
  over 600 ticks, random bytes, truncated and extended real messages,
  oversized inputs, another player's id, acknowledgements of ticks never
  sent, far-future stamps, absurd counts, resync floods, a host's message
  kind and hostile values: the host never panics, reports each diagnostic,
  never lets the forged input move another player, keeps the attacker's own
  values clean, bounds resyncs, passes non-replication kinds on, resolves
  forged network ids to nothing the attacker may not see, and the honest
  clients converge afterwards.
- **Real UDP** (`tests/udp.rs`): a host and two clients over `127.0.0.1`.
- **Input** (`tests/input.rs`): frames written by the host equal what
  `wish_input::apply_players` writes for the same values (cleaning, edges,
  the world hash); one player writes nothing new.
- Unit tests: varints, layouts, value encoding between worlds, invalid bytes
  refused by the world, 20 000 random messages never panic the decoders.

## 9. Not done here

- Prediction, reconciliation, interpolation, tick sync: built in package
  11 ([1.1-prediction.md](1.1-prediction.md)) on the seams left here (the
  input acknowledgement in every state message, states kept by tick), plus
  the complete flag of the state header.
- Hierarchy: replicated entities are sent flat (a child's `Transform` is
  relative to a parent the client may not have). Replicating parent links is
  left for when the yardstick game needs it.
- Resources and events are not replicated; game state that clients need goes
  on a replicated entity, and targeted messages are package 12.
- The list of replicated types comes from the host's configuration; reading
  it from `wish.json`, a `net` tool, scenario tests with bots and the
  editor's network panel are package 14.
- Leaving and rejoining with the same player id is the lobby's (package 12);
  here a player id is freed when its peer disconnects.
- Distance does not raise priority yet (nearer first); the yardstick game's
  measurement decides whether it is needed.
- Not run on Linux in this package (the crate has no platform code; the
  transport's UDP test is the platform-dependent part).
