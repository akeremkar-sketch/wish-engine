# M7 — A game made with our own engine

Status: done (16 November 2026). Branch: `m7-game`. Related decisions: ADR-016 (input), ADR-017 (testing), ADR-020 (3D first), "First showcase game: a small 3D platformer" (DECISIONS, 10 November 2026).

## 1. Goal and method

M7 tests the engine by **using** it: one showcase game, two small examples, an evaluation suite of 40+ tasks, a friction log with its fixes, and a short engine guide.

**Method (user decision, 16 November 2026):** the agent in this working session (Opus 5.5) builds the showcase game **only with the engine's own tools**. Scene changes use `edit_apply`. Observation uses `capture_frame`/`describe_view`/`entity_query`. Game code uses file editing + `script_build`. Proof comes from scenario tests. This is how an outside agent would work. The scene file is never written by hand. Every place where the agent gets stuck goes into the **friction log** (`docs/friction.md`) and is fixed in the **engine**, not in the game (a missing tool, a weak error message, wrong documentation, a bug). The real measurement with Sonnet 5.5 · medium and Haiku 5.5 (the evaluation suite + "make a game" tasks) runs once at the end of M7, with the user's approval (it uses quota).

**Exit criteria (ROADMAP):**
1. The showcase game can be played from start to end and its scenario tests pass.
2. Evaluation suite: Sonnet 5.5 · medium ≥ 90%; Haiku 5.5 results are recorded. (Run: at the end, with approval.)
3. Basic tasks are verified with at least one MCP client other than Claude. (Client setup is put to the user for approval.)
4. Comparative measurement: an engine-independent subset also runs on the MCP connections of Unity and Unreal. (Setup is put to the user for approval; it is a measurement and does not grow the 1.0 scope.)

## 2. Showcase game: "Ada Atlama" (working name)

A short 3D platformer, 2–4 minutes long. It tests physics, camera, input, audio, interface, particles and animation together.

- **Player:** uses the character controller (M6). Runs, jumps, has a little air control. After a fall it restarts from the last checkpoint.
- **Camera:** a third-person camera that follows the player from behind and above, with smooth following (game code).
- **Level:** small islands in the sky. Fixed platforms, **moving platforms** (kinematic body driven by game code; they must carry the character), a falling/vanishing platform, a hazard (spikes or lava → restart), checkpoints (a flag), a finish gate.
- **Collectibles:** crystals (sensors), with a counter in the interface. All of them + the finish = a win screen (time and crystal count).
- **Audio:** jump, pickup, fall, music (short WAV files generated by code; no downloads).
- **Visuals:** primitive shapes + materials + point lights. Particles on pickup and at the finish. A simple glTF generated by code if needed.
- **Proof:** scenario tests (the level can be finished, a fall returns to the checkpoint, the moving platform carries, the interface counts correctly), a recorded full playthrough replay (bit-identical in CI), a golden image.

Asset production needs no downloads. If real models or sounds are wanted later, the user is asked.

## 3. Friction log

`docs/friction.md`: each row is one snag. Fields: **no**, **what happened** (the call, the message, what was expected), **kind** (missing tool / weak message / wrong or missing documentation / bug / API gap / performance), **impact** (how many steps or attempts it cost), **fix** (commit), **status**. Rule: the same snag must not happen twice. Each fix is protected by either a test or an evaluation task. At the end of M7 the log is merged with the results of the Sonnet/Haiku runs.

## 4. Expected engine work (decided by measuring)

Known candidates. They are done only if really needed. If not needed, the log says "not needed":
- A moving platform carrying the character (Rapier character controller + kinematic platform velocity).
- Updating the character collider in queries within the same tick (M6 finding 8).
- Nested prefabs (left in M2 to be measured) — for island/platform clusters.
- Cascaded shadow maps (CSM) — shadow quality in an open sky scene (left in M3 to be measured).
- Game code helpers (for example `lerp`/`look_at` for smooth following), a platformer recipe in the guide.
- Applying `edit_apply` to a live session (passed to M8a; moving it earlier may be considered if the showcase game needs it).

## 5. Two small examples

They test areas different from the showcase game: (a) **2D brick breaker** (orthographic camera, sprites, 2D physics locks, interface, audio); (b) **a small interface-heavy game** (menu, buttons, text; for example a quiz or a timed clicking game). Both have tests, and both are recorded and replayed in CI.

## 6. Evaluation suite 40+

Tasks 26–40+: platformer building blocks (follow camera, moving platform, checkpoint, win screen, hazard), cases that come from the friction log, small games like the two examples. All are proven with `selftest`. Measurement: at the end, Sonnet 5.5 · medium (target ≥ 90%) and Haiku 5.5 (recorded).

## 7. Another MCP client and the comparison

- **Another client:** candidates are MCP Inspector (official, needs Node) and the agent modes of VS Code / Cursor. The user is asked about setup in that work package.
- **Unity/Unreal comparison:** engine-independent tasks (place a cube, adjust a light, make an entity visible, a box that falls with physics…) run with the same model on three engines. Success, steps, tokens and error counts are shown side by side. Unity/Unreal setup and MCP connections are put to the user for approval in that work package.

## 9. Risks

| Risk | Mitigation |
|---|---|
| The building agent (Opus) knows the engine "too well" and misses friction | Rule of working only with tools; every failed call and every "I had to look at the source" moment goes into the log; checked at the end with the Sonnet/Haiku measurement |
| Moving platforms have problems with the character controller | Tried early (WP1–WP2); if needed, the platform velocity is passed to the character on the engine side |
| Scope grows (the showcase game "never ends") | The level is 2–4 minutes; a new mechanic only if it reveals a gap in the engine |

## 10. Implementation notes

### WP1–WP3 — the showcase game "Ada Atlama" (`examples/islands`)

- **How it was built:** only with tools, using `wen do` (several calls in one process; sessions live as long as the process). The scene used `edit_apply`, sounds used `asset_create`, code used `scripts/src/lib.rs` + `script_build`, observation used `capture_frame`/`describe_view`/`entity_get`, proof used `test_run`. The scene file was never touched by hand.
- **The game:** start island → two-step island → kinematic elevator (game code drives it by time: wait, ease to the top, wait, return) → finish island and gate. Six crystals (sensors; sound + sparkle), a checkpoint flag (respawn point), a return to the checkpoint when falling out of the world, a follow camera (smoothing independent of time), a crystal counter in the interface, wind sound, a win screen (crystal count + time).
- **Proof:** 4 scenario tests (`first_jump`, `checkpoint`, `win` — the whole level, six crystals, the golden image of the win screen) and the CI test `the_islands_showcase_is_won_by_its_tests_and_replays` (build, check, tests, bit-identical replay of the recorded playthrough).
- **Friction log F1–F8** (all fixed in the engine; F8 was work expected in the design): `wen do` readable JSON; game systems in the project guide; a note on tools that read the scene while a session is open; contact event jitter on a walking character; **new tool `asset_create`**; SDK `asset()`; **`entity_get` reads resources**; **a moving platform carries the character exactly** (Rapier's half-way following is turned off, and the platform's real displacement is used; exact at 6.5 m in 3 s).
- **My own mistakes (not the engine's):** the camera position in a test expectation; route directions; the respawn point overlapping a crystal; the crystal path touching the finish sensor. These were game design/play mistakes. The tools' error messages (step, tick, values read) showed each one at a glance — a good sign.

### WP4 — recipes and guide

- **`wish://docs/recipes`** (`crates/wish_control/src/recipes.md`): eight working pieces — platformer character, follow camera, collectibles + score text + sound + sparkle, falling and checkpoints, moving platform, win screen and start button, 2D scene, scenario tests and replays. Each is a full `scripts/src/lib.rs` plus scene operations. The code comes from pieces proven in the showcase game.
- **Recipes do not rot:** `wish_control/tests/recipes.rs` builds the code of every recipe in an empty project (without warnings), applies its operations, checks the project and runs a session. It also tests the shape of the test examples. On its first run it caught a real bug in the 2D recipe (`ground` already exists in a new project).
- **Discoverability:** in the MCP resource list, in `docs_search` (section by section), in the guide with a short "Game systems" section, in the new project's `CLAUDE.md` and in the MCP server instructions. Names from other engines (`FollowCamera`, `MovingPlatform`, `Checkpoint`, `Cinemachine`…) point to the recipes through a concept hint.

### WP5 — two small examples

- **`examples/bricks` (2D brick breaker):** orthographic camera, sprites, 2D physics locks (Z translation, all rotations), a ball with `ccd` and a bounce coefficient of 1, a constant-speed ball, and the paddle giving direction by hit position (game code), a score/lives interface, sounds (`asset_create`), a win/lose panel. Tests: boot, and **a full game with an automatic pilot** (40 bricks, ~5,000 ticks). In the first try the automatic pilot got into an endless loop (a flat paddle always reflects the ball at the same angle) → the classic fix; this was game design, not the engine.
- **`examples/quiz` (interface-heavy):** menu → five questions × four answer buttons → result. Everything is a `UiNode`. Game code only reacts to `ButtonClicked` and writes text. The tests play by clicking with the pointer (all correct 5/5 and one wrong 4/5).
- **CI:** both are built, their tests run, and the recorded run is replayed bit-identically (`script_tools.rs`).
- **Friction F9–F10 (fixed):** the order of interface children was undocumented (`order`); the hint for a file with invalid UTF-8 did not mention the encoding.

### WP6 — evaluation tasks 26–41

- 16 new tasks (`crates/wish_evals/src/m7_tasks.rs`); total **41**; **`selftest` 41/41** (each task first fails against the reference solution, then passes). All of them check what the engine did (session run, `describe_view`, logs, hidden scenario tests).
- **Game code (6):** follow camera, moving platform, respawn on fall, gem pickup with a sensor + `Score`, jump by impulse (`BodyImpulse`), a seconds counter text (`text()`).
- **Scene/tool (10):** a bell sound with `asset_create` (pitch and length are measured) and a ring picture + showing it in the interface, reading the source of a running game and writing a note (`entity_get resources`), a vertical menu (interface order `order`), a 2D bounce (locks), a scene light cone, playing an animation once, a "ghost" ball with collision layer/mask, a second level scene, a replay record.
- Most come from the friction log: the places where an agent may get stuck (F5 asset_create, F7 resources, F9 order…). **The real run (Sonnet · medium, target ≥ 90%; Haiku, recorded) uses quota → at the end of M7, with the user's approval.**

### WP7 — another MCP client and the comparison rig

- **Another client (exit criterion 3): MCP Inspector 2.13.0** (official; installed to `C:\wish-build\mcp-inspector` with the user's approval, deleted when the work was done), CLI mode; each step is a fresh `wen mcp` process (the handshake happens every time). `tools/mcp_inspector_check.py`: the tool list with a `--strict` schema portability check (25 tools, no problems), resources + guide reading, prompts, `project_info`, `schema_get`, `edit_apply` + `entity_get`, error code + hint, `describe_view` + `capture_frame` (PNG), `script_build`, `test_run` (a falling box + a game code counter), `asset_create` + `check` → **11/11** (`evals/results/m7-mcp-inspector.md`). No change was needed in the engine.
- **Comparison rig (exit criterion 4):** `tools/compare/` — 8 engine-independent scene tasks (place a cube, paint, a falling box, a point light, turn the camera to a target, change a parent, delete, scale). The same text and the same starting scene on both engines (Z mirrored in Unity; `unity/CompareSetup.cs`). The Wish check uses the engine's tools. The Unity check reads the saved `.unity` file (a small YAML reader that needs no setup). The runner collects success, turns, tool calls/errors, tokens and cost. `selftest` is free and passes (Wish: 8 tasks fail before / pass after; Unity: the reader on a sample file). Before the Unity project, the real run checks that the reader finds every task *failing* on the real starting scene.
- **No Unreal** (user decision: not enough disk, the install is 50+ GB). The Unity run (a temporary project of ~2–3 GB, deleted afterwards) and the Wish run use quota → in WP8, with the user's approval.
- **Disk:** at the start of WP7 `target/debug` had grown to 104 GB (cargo does not delete old build variants). It was cleaned, and `tools/clean-build.ps1` and a CLAUDE.md rule were added.

### WP8 — closing review

Two independent reviewers (read-only; one on the engine code, one on examples + recipes + evaluation + rig): **26 findings** (engine 8, others 18), all addressed.

- **Engine (regression tests `wish_physics/tests/world.rs`, `wish_control/tests/m7_tools.rs`):**
  - The moving platform carry did not see walls/ceilings (the character was carried into a wall) → the carry is swept with the character's shape and clipped at the first obstacle (`a_moving_platform_does_not_carry_its_character_through_a_wall`, a ceiling-crush test).
  - The platform the character stood on was searched *after* the step, against the platform at its new pose (a fast sinking platform went beyond the ray range) → it is found **before** the step, while the query tree still knows the old poses (`a_sinking_platform_keeps_its_character`, 15 m/s).
  - The contact offset was set after the first step (the events of the first tick were different) → it is set when the collider is built/mapped. A side effect (bodies resting against the character stand 2× the offset away) is in the documentation.
  - When the scene had no character, the kind of the platforms still changed every tick (this stopped them from sleeping) → only while a character exists.
  - `asset_create`: `dry_run` and a failed call created folders → `inside_project` now only checks, and `prepare_output` creates the folder right before writing (capture/golden/replay writes use it too). An unknown field inside `sound`/`picture`, a name that is not a string, and a definition that does not match the file type are rejected (the hint names the close name). A path that already exists on disk with a different letter case is rejected (so that it does not work on Windows and break on Linux).
  - `entity_get resources`: the default is returned only in the "not in the world" case, and it is reported with `resources_defaulted`. Any other error is returned as an error.
  - Remaining (low): a rotating platform does not turn the character's heading (yaw) — noted.
- **Recipes:** the test now **plays** every recipe (the runner runs/jumps, coins are collected and the text changes, the checkpoint brings the character back, the platform is in place on time, the button starts, the 2D ball bounces; 7 recipes). The checkpoint recipe got a note about the `respawn` default and "set to start", and the win recipe a note that the game sets `won`.
- **Examples:** in Bricks the first key takes the paddle over from the automatic pilot (`keys.test.json`), and the paddle sound plays only on the paddle. The Islands/Bricks end text is found with a marker component (`WinText`/`EndText`). In Quiz the "Play again" button is tested.
- **Evaluation tasks:** 26 camera world position + the player in the image (a child camera is accepted too), 28 the velocity reset is checked, 30 noise does not count as a bell, 31 exactly 64×64, 32 the value cannot be guessed (the checker reads it itself), 34 the lock must stop the z drift, 35 the height is taken from the top of the entity, 37 a cheat without a sensor/collider is not accepted, 38 the highest point with `until`, 40 the copies must be identical, 41 exactly 81 ticks. The agent's own test must contain `expect`/`until` (all game code tasks). `selftest` **41/41**.
- **Comparison rig:** the Unity camera check uses the real horizontal/vertical field of view. In the falling box task a trigger/locked Y is rejected. Materials inside the scene are read. Both agents run from an empty, neutral folder with file reading tools turned off. The starting scene is saved as text and it is checked that the reader finds the entities. Rows are written as soon as they finish, and a timeout does not stop the run.
